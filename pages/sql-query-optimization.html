Query Optimization

Reading an EXPLAIN plan well enough to spot a full table scan, and the N+1 query pattern — one query per row instead of one query total — which is the single most common real-world "why is this so slow" root cause an SDET will actually encounter, usually hiding behind an ORM.

Concept

SQL is declarative — the query says what to fetch, and the query planner decides how. Optimization is entirely about influencing that "how": giving the planner useful indexes, and writing queries in a shape it can actually use them for. Everything on this page is either about reading what the planner decided, or avoiding query patterns that quietly defeat it.

Reading EXPLAIN

EXPLAIN ANALYZE
SELECT * FROM orders WHERE customer_id = 42;
Plan (no index on customer_id)Plan (with an index)
Seq Scan on orders
(cost=0.00..2500.00 rows=1 width=64)
Filter: customer_id = 42		Index Scan using idx_orders_customer_id
(cost=0.42..8.60 rows=1 width=64)
Index Cond: customer_id = 42

Seq Scan means every row in the table was read to check the filter — this is the literal full-table-scan mechanic from Database Design. Index Scan means the planner used an index to jump straight to matching rows. The cost numbers (arbitrary planner units, not milliseconds) show the difference directly: 2500 vs 8.6 — roughly 300× cheaper in the planner's own estimate for this one query.

EXPLAIN shows "Seq Scan" on a WHERE clause filtering a column you know has an index on it. What's the most likely explanation?

The N+1 query problem

Fetch 3 customers, then — inside a loop, one at a time — fetch each customer's orders separately. 3 customers means 1 + 3 = 4 total queries; 1,000 customers means 1,001. This is overwhelmingly the most common real-world query performance bug, and it almost always comes from an ORM's lazy-loading default rather than hand-written SQL:

-- The fix: fetch everything in ONE query with a join, instead of N+1 round trips
SELECT c.name, o.id AS order_id, o.amount
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;
Where an SDET actually encounters this A test that looks correct in isolation can reveal an N+1 problem indirectly — a page-load or API-response-time test that passes fine with 5 seeded test rows and fails a performance budget once seeded with 5,000. That symptom, more than reading application code, is often the first real signal something's fetching data in a loop.

Index strategy, beyond the basics

ConceptWhat it means
Composite indexAn index on (customer_id, status) together speeds up queries filtering on both — but generally only helps if the query filters on customer_id first (leftmost-prefix rule); an index on (A, B) usually doesn't help a query that only filters on B.
Covering indexAn index that includes every column a query needs lets the database answer entirely from the index, without touching the actual table rows at all — meaningfully faster for read-heavy queries on wide tables.
Function on an indexed columnWHERE UPPER(email) = 'ADA@X.COM' generally can't use a plain index on email — the stored value and the indexed value no longer match literally. A function-based (expression) index built specifically on UPPER(email) is the fix if this pattern is common.

Other common slow-query causes

CauseWhy it's slow
SELECT * on a wide tableFetches and transfers every column, including ones never used — real cost on wide tables or large result sets, and it also defeats covering indexes that would otherwise satisfy the query from the index alone.
A JOIN with no index on the join columnFalls back to a full scan of one side for every row of the other — see the "foreign key without an index" gotcha in Database Design.
A correlated subquery on a large tableCovered in Subqueries — potentially re-executes once per outer row.
Sorting or grouping without a supporting indexORDER BY / GROUP BY on an unindexed column requires sorting the entire result set in memory (or on disk, if it doesn't fit) rather than reading pre-sorted index order.

Interview Q&A

Junior What's the difference between a sequential scan and an index scan in an EXPLAIN plan?
A sequential scan reads every row in the table to check the filter condition. An index scan uses an index to jump directly to matching rows without reading the whole table. EXPLAIN's cost estimates make the difference visible directly, especially on larger tables.
Mid What is the N+1 query problem?
Fetching a list of N records with one query, then fetching related data for each record with a separate query inside a loop — N+1 total queries instead of one. It commonly comes from an ORM's lazy-loading default and scales linearly (and expensively) with the size of the initial result set. The fix is typically a JOIN or an explicit eager-load/batch-fetch of the related data in one additional query instead of N.
Mid Why might WHERE UPPER(email) = 'ADA@X.COM' fail to use an index on the email column?
A plain index on email stores the literal column values — applying UPPER() to the column at query time changes what's being compared, and the database generally can't match that against an index built on the untransformed values. A function-based (expression) index built specifically on UPPER(email) would be usable; the plain index on email is not.
Senior A performance test passes with a small seeded dataset but fails once the dataset is scaled up. What would you investigate first?
Whether the slow endpoint's data access pattern scales linearly per record rather than staying roughly constant — the classic signature of N+1 queries or a missing index that a full table scan can mask on a small table but not a large one. EXPLAIN on the actual queries involved, and a query log or APM trace showing the number of queries fired per request, would confirm it quickly.

Gotchas

N+1 hides inside ORM convenience methods Code that looks like simple object access (customer.orders) can silently be a full extra database round trip — this is invisible from reading the loop itself without knowing the ORM's lazy-loading behavior.
An index existing doesn't guarantee it gets used A function wrapped around the column, an implicit type mismatch, or the planner simply deciding a scan is cheaper on a small table can all result in an index being present but unused. Always verify with EXPLAIN rather than assuming.
Composite index column order matters An index on (customer_id, status) generally doesn't help a query filtering only on status — the leftmost column has to be part of the filter for the index to be usable in the typical case.
