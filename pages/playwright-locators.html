Playwright Core Locators

get_by_label, get_by_role, CSS locators, get_by_text — which one to reach for depends entirely on what the DOM actually exposes, not personal preference. The label-locator failure conditions are a genuine interview trap.

Concept

Playwright gives you several complementary ways to locate an element, ranked roughly by how "semantic" the underlying attribute is: a form field's associated label, a component's accessibility role, a raw CSS selector as a universal fallback, or the visible text an element contains.

Choosing a strategy

get_by_label

page.get_by_label("Username").fill("demo_user")
page.get_by_label("Password").fill("demo_pass123")

This only works if one of two DOM conditions is true:

  • The <input> is nested inside the <label> tag, or
  • The <label for="id"> attribute exactly matches the input's own id attribute.
Real failure case from this lecture On a second practice page, the label's for attribute was "email" but the input's actual id was "userEmail" — a mismatch. Since the input also wasn't nested inside the label, get_by_label failed to find it despite a label being visibly present on the page.
HTML: <label for="email">Email</label> <input id="userEmail"> (input not nested inside the label). Does page.get_by_label("Email") find this input?

get_by_role

page.get_by_role("combobox").select_option("teach")
page.get_by_role("button", name="Sign In").click()
page.get_by_role("link", name="Terms and Conditions").click()

Identifies an element by its accessibility/semantic role — combobox, button, link, checkbox, alert, image, and more. When multiple elements share the same role (e.g. several buttons on a page), the optional name= parameter filters down to the one whose visible name matches — role and filter are bundled into the single call.

For dropdowns, .select_option() selects by the underlying HTML <option value="..."> attribute — which is not necessarily the same string as what's visually displayed to the user.

Beyond this video — common ARIA roles, not just the 3 named in the course The video names combobox, button, link, checkbox, alert, and image. The full role vocabulary is much larger — the ones you'll actually hit most often in real apps: textbox, radio, heading, list / listitem, tab / tabpanel, dialog, table / row / cell, navigation, banner, search, menu / menuitem, and progressbar. Any element with an implicit or explicit ARIA role can be targeted this way — worth knowing since interviewers sometimes ask "how would you locate X" for elements that aren't literally form controls.

CSS locators

The universal fallback — works on anything, including custom components with no ARIA role (e.g. plain <div> cards). Derived directly from DOM attributes via page.locator(css_selector):

DOM attributeCSS selector syntaxExample
id="terms"#id#terms
class="text-info".class-name.text-info
tag namebare tag namerarely unique — not much preferred

For a checkbox specifically, Playwright provides a semantic .check() action (in addition to the generic .click()) that specifically validates and checks a checkbox element:

page.locator("#terms").check()

To grab an element purely by its visible text (e.g. an alert/message block, without knowing its CSS class):

page.get_by_text("Incorrect username or password")

get_by_placeholder

The natural fallback when a field has no label at all — common on search boxes and compact forms where the placeholder text is the only visible hint:

page.get_by_placeholder("Hide/Show Example").fill("some text")

It's also the practical rescue for the broken-label case from earlier on this page: when for/id don't line up, the placeholder is often still a clean, unique handle — no CSS selector required.

Placeholder is not text A placeholder is a greyed-out hint that disappears when you type. It is not the element's text content, so get_by_text() won't find it — that's why it needs its own dedicated locator.

Actions beyond click and fill

Once a locator resolves, several actions beyond .click() and .fill() come up regularly:

ActionWhat it's for
.hover()Moves the mouse over an element without clicking — the way to open mega-menus and hover-triggered dropdowns before clicking an item inside them.
.check() / .uncheck()Semantic checkbox/radio actions. Unlike .click(), they verify the resulting state rather than blindly toggling.
.select_option()Chooses from a <select> by its underlying value attribute.
.text_content()Returns the element's text as a string — see Child Windows.

The hover-then-click pattern, in full:

page.locator("#mousehover").hover()                       # opens the menu
page.get_by_role("link", name="Top").click()              # click an item inside it
Why hover needs to be explicit Auto-waiting checks that an element is visible and actionable — but a menu item that only renders on hover isn't visible until you hover. Playwright won't infer that a hover is required, so the hover has to be its own step.

The rest of the get_by_* family

Beyond this video — standard Playwright API, not covered in the course
  • get_by_alt_text("Company logo") — matches an <img> by its alt attribute.
  • get_by_title("Close dialog") — matches an element by its title attribute (the tooltip text).
  • get_by_test_id("submit-btn") — matches a custom test-id attribute (data-testid by default). The most resilient option when a team deliberately adds test hooks, since it doesn't depend on visible text, styling, or DOM structure at all.

Preference order most teams converge on, roughly: get_by_role (closest to how a real user/assistive tech perceives the page) → get_by_label / get_by_placeholder for form fields → get_by_test_id when the team maintains them → CSS as the last resort.

Interview Q&A

Junior What two DOM conditions must hold for get_by_label to successfully find an element?
Either the input element is nested inside the <label> tag itself, or the label's for attribute exactly matches the input's id attribute. If neither holds, get_by_label won't find it — even if a label is visually present on the page.
Junior How do you disambiguate multiple elements that share the same role, like several buttons on a page?
Pass the name= parameter to get_by_role, e.g. get_by_role("button", name="Sign In") — Playwright gets all elements with that role first, then filters to the one whose visible/accessible name matches.
Mid When would you fall back to a CSS locator instead of get_by_role or get_by_label?
When the element is a custom component with no semantic ARIA role attached — e.g. a plain <div>-based product card — or a form field with no associated label. CSS built from id/class attributes works regardless of role or label semantics.
Junior What's the difference between what select_option chooses and what's visually shown in a dropdown?
select_option targets the underlying HTML option value attribute, which is not necessarily identical to the text visually displayed to the user in the dropdown UI.
Junior A search box has no label and no text content. How do you locate it?
get_by_placeholder("...") matches on the greyed-out hint text inside the field. It's the right choice when no label exists, and also a clean workaround when a label exists but its for/id linkage is broken. Note a placeholder isn't the element's text content, so get_by_text() won't find it.
Mid How do you click an item in a menu that only appears on mouse hover?
Two steps: .hover() on the trigger element to open the menu, then a normal locator + .click() on the item inside it. Auto-waiting won't infer that a hover is needed — it checks whether an element is visible and actionable, and a hover-only menu item genuinely isn't visible until the hover happens, so the hover must be its own explicit step.
Junior Name the full get_by_* family.
get_by_role, get_by_label, get_by_text, get_by_placeholder, get_by_alt_text, get_by_title, and get_by_test_id. Plus the generic locator() which takes a raw CSS or XPath selector.
Mid Rank the locator strategies by preference and justify the order.
Roughly: get_by_role first, because it matches how a real user and assistive technology perceive the page — so it breaks only when actual user-facing behaviour changes. Then get_by_label/get_by_placeholder for form fields, still user-visible. Then get_by_test_id where the team maintains dedicated hooks — completely stable but invisible to users, so it tests nothing about accessibility. CSS/XPath last, because it couples tests to internal DOM structure and styling, which change for reasons that have nothing to do with behaviour.
Scenario A form field has a visible "Email" label on screen, but get_by_label("Email") finds nothing. Walk through your diagnosis.
The label is rendering, so the problem is the association, not the text. Inspect the DOM and check the two valid linkages: (1) is the input nested inside the <label>? (2) does the label's for value exactly match the input's id? The classic failure is a near-miss like for="email" against id="userEmail" — visually fine, functionally unlinked. Fixes: correct the HTML if you own it (which also fixes real accessibility for screen-reader users), or work around it with get_by_placeholder, get_by_role("textbox"), or a CSS selector on the id.
Scenario Your get_by_role("button") call suddenly fails after a UI update that added a second button. What happened and how do you fix it?
Playwright runs in strict mode by default — a locator resolving to multiple elements raises a strict-mode violation rather than silently acting on the first one. That's deliberate: it surfaces ambiguity instead of letting a test quietly click the wrong thing. Fix by narrowing: add name= (get_by_role("button", name="Sign In")), scope the search to a container first, or use .filter(). Reaching for .first "makes it pass" but reintroduces exactly the positional fragility you were avoiding.
Senior A team's suite is full of CSS selectors like div.container > div:nth-child(3) > button and breaks constantly. What do you change and how do you argue for it?
Those selectors encode DOM structure, so any layout refactor breaks them even though behaviour is unchanged — high maintenance cost, zero behavioural signal. Migrate to role/label-based locators so tests bind to what users actually perceive, and introduce data-testid for genuinely ambiguous elements. The business argument is maintenance cost and trust: a suite that fails for non-bugs gets ignored, and an ignored suite provides no safety net. Practical rollout is incremental — convert as you touch tests, not a big-bang rewrite — and adding roles/labels often improves real accessibility as a side effect.

Gotchas

Watch out A visually-present label doesn't guarantee get_by_label will work — always check whether the input is actually nested in the label or correctly linked via for/id before assuming this locator is usable.
Watch out Bare tag-name CSS selectors are rarely unique on a real page (multiple labels, multiple divs, etc.) — prefer id or class-based selectors unless you're deliberately grabbing every match.
