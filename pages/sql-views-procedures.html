Views, Procedures, Functions & Triggers

The database-object family beyond plain queries — and specifically why an SDET should care: these are the tools for building reusable test-data setup helpers and validation logic that live in the database itself, not just application code.

Concept

Four different ways to package SQL logic so it doesn't have to be rewritten every time: a view packages a query, a stored procedure packages a sequence of statements (including writes), a function packages a reusable computation that returns a value, and a trigger packages logic that runs automatically in reaction to a DML event.

Regular views

A saved query, nothing more — a view has no data of its own. Every time it's queried, the database re-runs the underlying SELECT against the live tables.

CREATE VIEW shipped_orders AS
SELECT id, customer_id, amount
FROM orders
WHERE status = 'shipped';

SELECT * FROM shipped_orders;   -- reads exactly like querying a table

Because it's just a stored query, a view is always up to date — there's no staleness to worry about, since it never actually stores a result.

Materialized views

The opposite trade-off: a materialized view does store its result physically, like a real table — which makes it fast to query (no re-running the underlying logic every time) at the cost of going stale the moment the source data changes, until it's explicitly refreshed.

CREATE MATERIALIZED VIEW monthly_revenue AS
SELECT DATE_TRUNC('month', created_at) AS month, SUM(amount) AS total
FROM orders
GROUP BY 1;

REFRESH MATERIALIZED VIEW monthly_revenue;   -- re-runs the query, overwrites the stored snapshot

Watch the difference directly — a new order is inserted, then both view types are queried immediately afterward:

Stored procedures

A named, callable sequence of SQL statements — unlike a view, a procedure can perform writes and contain actual procedural logic (conditionals, loops), not just a single query:

CREATE PROCEDURE archive_old_orders(cutoff_date DATE)
LANGUAGE SQL
AS $$
  INSERT INTO orders_archive
  SELECT * FROM orders WHERE created_at < cutoff_date;

  DELETE FROM orders WHERE created_at < cutoff_date;
$$;

CALL archive_old_orders('2025-01-01');

Both statements run as one unit when the procedure is called — the caller doesn't repeat this multi-step logic inline every time archiving needs to happen.

User-defined functions

Similar idea to a procedure, but a function specifically returns a value and can be used directly inside a query — a procedure generally can't be:

CREATE FUNCTION order_tier(amount NUMERIC) RETURNS TEXT
LANGUAGE SQL
AS $$
  SELECT CASE
    WHEN amount >= 1000 THEN 'high'
    WHEN amount >= 100  THEN 'medium'
    ELSE 'low'
  END;
$$;

SELECT id, amount, order_tier(amount) FROM orders;   -- used inline, like a built-in function

This is the same logic as the CASE WHEN example from Fundamentals — wrapped in a function so every query needing this classification calls one name instead of repeating the CASE expression everywhere.

Triggers

Logic that fires automatically in response to a DML event — INSERT, UPDATE, or DELETE — without the application needing to remember to call anything:

CREATE TRIGGER log_salary_change
AFTER UPDATE OF salary ON employees
FOR EACH ROW
EXECUTE FUNCTION record_salary_history();

-- Now ANY update to salary — from any application, any script, any person —
-- automatically writes an audit row, with zero cooperation required from the caller

The defining property of a trigger, for better and worse, is that it's invisible from the statement that caused it — UPDATE employees SET salary = 90000 WHERE id = 5 looks like an ordinary update, but a trigger can make it also insert an audit row, block the update entirely, or modify other tables, none of which is visible by reading that one line of code.

Why an SDET actually uses these

ObjectTest-related use
ViewA stable, simplified "test data view" — e.g. active_test_users — that hides the real schema's complexity from test setup code.
Stored procedureA reusable seed_test_account(...) or reset_test_data() procedure, callable identically from any test framework or language, instead of duplicating multi-step setup SQL in every test suite.
FunctionShared validation logic (e.g. a function that computes an expected derived value) usable both by the application and directly in a test's assertion query.
TriggerUnderstanding these matters even without writing them — a trigger can be the actual, hidden reason a test's direct INSERT doesn't produce the side effects the application's normal code path does, or vice versa.

Interview Q&A

Junior What's the difference between a view and a materialized view?
A regular view stores no data — it's a saved query that re-runs against live tables every time it's queried, so it's always current. A materialized view stores its result physically, like a table, making it fast to query but stale until REFRESH MATERIALIZED VIEW is explicitly run.
Junior What's the difference between a stored procedure and a function?
A function returns a value and can be used inline inside a query, like SELECT order_tier(amount). A stored procedure is called on its own (CALL procedure_name(...)), can perform writes and multi-step procedural logic, and generally can't be embedded inside another query's expression the way a function can.
Mid What is a trigger, and what's a real risk of relying on them heavily?
A trigger is logic that fires automatically on an INSERT/UPDATE/DELETE event, without the caller needing to invoke anything. The risk is invisibility — reading the statement that caused it gives no indication a trigger ran at all, which can make debugging unexpected side effects (extra rows written, an update silently blocked) considerably harder, especially for someone unfamiliar with the schema's triggers.
Senior When would you choose a materialized view over just running the aggregation query directly each time?
When the underlying query is expensive (a large aggregation, several joins) and queried often, but doesn't need to reflect every single write in real time — a dashboard refreshed hourly is a good fit; a live balance check is not. The trade-off is explicitly accepting staleness between refreshes in exchange for consistently fast reads.

Gotchas

A materialized view can look "broken" without a refresh schedule If nothing ever calls REFRESH (manually or via a scheduled job), the view silently drifts further and further out of date — not an error, just quietly wrong.
Triggers hide side effects from the caller A test that inserts directly into a table can accidentally skip logic a trigger normally provides — or, less obviously, trip a trigger the test author didn't know existed.
Overusing views doesn't reduce actual query cost A regular view is not a performance optimization — querying it costs exactly what querying its underlying SELECT costs. The performance win, when there is one, comes specifically from materialized views.
