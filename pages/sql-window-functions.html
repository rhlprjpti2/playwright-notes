Window Functions

The feature that separates "knows SQL basics" from "has actually worked with real reporting queries" in most senior interviews. One idea makes all of it click: a window function computes a value across a set of related rows without collapsing them — every row survives, unlike GROUP BY.

Concept

-- GROUP BY: 4 rows in, 1 row out per department — individual rows are GONE
SELECT department, AVG(salary) FROM employees GROUP BY department;

-- Window function: 4 rows in, 4 rows out — every employee keeps their own row,
-- each one annotated with a value computed across their department
SELECT name, department, salary,
       AVG(salary) OVER (PARTITION BY department) AS dept_avg
FROM employees;

That's the entire concept: OVER (...) turns an aggregate into something that annotates each row instead of replacing many rows with one. Everything else on this page is a variation of "what gets computed per row, over what set of related rows."

PARTITION BY

PARTITION BY splits the rows into independent groups — the window function then resets and operates separately within each group, the same way GROUP BY would bucket rows, except no rows are collapsed. Ranking restarts at 1 for every partition:

LEAD and LAG

Reach into an adjacent row — the next one (LEAD) or the previous one (LAG) — without a self-join. Classic use: month-over-month comparison.

SELECT month, revenue,
       LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue,
       revenue - LAG(revenue) OVER (ORDER BY month) AS change
FROM monthly_revenue;

January's LAG(revenue) is NULL because there's no row before it — the same "no prior row exists" reasoning as any other unmatched-row NULL. Before LEAD/LAG existed as built-ins, this required a self-join on a manually computed "previous row" key — considerably more code for the same result.

Interview Q&A

Junior What's the fundamental difference between a window function and GROUP BY?
GROUP BY collapses multiple rows into one row per group — individual rows are gone. A window function (using OVER) computes a value across a related set of rows but keeps every original row intact, annotating each one with the computed value instead of replacing many rows with one.
Mid Two rows tie for 1st place. What does the next row get under RANK() vs DENSE_RANK()?
RANK() gives it 3 — it skips a rank number for every tied row above it, since 2 rows already occupy rank 1. DENSE_RANK() gives it 2 — it never skips, incrementing by exactly 1 from the previous distinct rank regardless of how many rows shared it.
Mid What does PARTITION BY do, and how is it different from GROUP BY?
PARTITION BY splits rows into independent groups for a window function to operate within — ranking, running totals, etc. restart per partition. Unlike GROUP BY, no rows are collapsed; every original row is still present in the result, just annotated with a value computed relative to its own partition.
Mid How would you find the top 2 highest-paid employees per department?
Wrap a RANK() or ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) in a CTE or subquery, then filter the outer query WHERE rank <= 2. Window functions can't be referenced directly in WHERE (same execution-order reasoning as aggregates and HAVING), so the filter has to happen in an outer layer.
Senior How would you calculate month-over-month percentage growth in revenue?
LAG(revenue) OVER (ORDER BY month) to get the prior month's value on the same row, then compute (revenue - prev_revenue) / prev_revenue directly — no self-join needed. The first row's LAG result is NULL (no prior row exists), so the growth calculation for that row is also NULL, which is the correct, honest answer rather than a fabricated 0% or 100%.

Gotchas

Window functions can't be filtered directly in WHERE Same execution-order reasoning as aggregates — WHERE runs before window functions are computed. Filtering on a window function's result requires wrapping the query in a CTE or subquery and filtering the outer layer.
RANK() leaves permanent gaps after any tie If exactness matters (e.g. "the 3rd highest-paid employee" as a literal row count), RANK's skipped numbers can silently point at the wrong row when ties exist upstream — DENSE_RANK or ROW_NUMBER may be the more correct choice depending on what's actually being asked.
Forgetting ORDER BY inside OVER() ROW_NUMBER, RANK, LEAD, and LAG are all inherently order-dependent — omitting ORDER BY inside OVER(...) leaves the row ordering undefined, and results can vary between runs.
