Playwright Auto-Waiting & Assertions

Back on Why Playwright & Why Python, auto-waiting was flagged as one of the two genuine differentiators from Selenium. This is the technical detail behind that claim — what Playwright actually checks before acting, and why it means no explicit wait code.

Concept

Before performing most actions (click, fill, check, etc.), Playwright runs a series of actionability checks on the target element: is it visible, is it stable (fully finished loading/animating, not still moving), does it receive events (nothing else obscuring it), and is it enabled (not disabled). If any check fails, Playwright automatically retries — it does not fail immediately the way a naive single check would.

In Selenium, none of this happens automatically — an immediate check on a not-yet-rendered element simply fails, and the developer has to hand-write explicit or implicit wait code to compensate.

The actionability check loop

Actions and assertions both go through the same loop: check, and if it fails, retry — automatically, with no wait code written by you. Step through what actually happens under the hood of the two lines below, from the wrong-credentials example on the login form.

Web-first assertions

Auto-waiting isn't limited to actions — Playwright's expect() assertions (imported from playwright.sync_api) are auto-retrying too. Instead of checking a condition once immediately, they retry until the condition becomes true or the timeout is reached:

from playwright.sync_api import expect

expect(page.get_by_text("Incorrect username or password")).to_be_visible()

This is what makes it safe to assert on something that appears with a short delay (e.g. an error message after a failed login) without writing any explicit wait beforehand.

The common assertions

Beyond to_be_visible(), a handful cover most real checks — and the pairs below are easy to confuse in an interview:

AssertionPasses when
to_be_visible()The element is rendered and visible.
to_be_hidden()The element is hidden or not in the DOM at all. The natural counterpart for testing show/hide behaviour — click Hide, assert hidden.
to_have_text("x")The element's text matches exactly.
to_contain_text("x")The text appears anywhere within — a substring match. Use this on broad locators like body, where exact full text is never what you mean.
to_have_count(n)The locator matches exactly n elements.
to_be_enabled() / to_be_disabled()The element is interactive / not interactive.
to_have_value("x")An input's current value matches — distinct from its text content.

A show/hide test reads exactly as you'd expect, with no waits despite the DOM changing between the two assertions:

expect(page.get_by_placeholder("Hide/Show Example")).to_be_visible()
page.get_by_role("button", name="Hide").click()
expect(page.get_by_placeholder("Hide/Show Example")).to_be_hidden()
Beyond this video — the actual default timeouts, per Playwright's docs The course estimates the global timeout as "roughly 7 to 10 seconds" without citing a source. The documented defaults are more specific and worth knowing precisely: actions (click, fill, check, etc.) default to a 30-second actionability timeout, configurable via page.set_default_timeout(ms) or a per-call timeout= argument. Web-first assertions (expect()) default to a separate, shorter 5-second timeout, configurable via assertion-level options or global test config. These are two independently configurable values, not one shared number.

Interview Q&A

Junior What does Playwright's automatic actionability check actually check for?
Per this course: visible, stable (finished loading/animating), receives events (not obscured by another element), and enabled. Playwright verifies these before most actions, retrying automatically until they pass or a timeout is reached.
Mid How is this different from Selenium's approach to synchronization?
Selenium has no built-in auto-wait for actionability — an immediate check on a not-yet-rendered or not-yet-stable element simply fails. The developer must write explicit or implicit wait code by hand to compensate. Playwright performs these checks and retries internally, with no synchronization code required from the test author.
Junior Does auto-waiting apply only to actions like click/fill, or also to assertions?
Both. Playwright's `expect()` assertions are "web-first" and auto-retrying — they recheck the condition repeatedly until it's true or the timeout is hit, rather than evaluating once immediately like a plain equality check would.
Mid If an element becomes ready in 2 seconds but the timeout is much longer, does Playwright wait out the full timeout?
No — Playwright proceeds the instant all actionability checks succeed. It only consumes the full timeout when the checks keep failing all the way until the deadline.
Mid What genuinely differentiates Playwright's auto-waiting from Selenium, in one sentence for an interview?
Playwright treats waiting for actionability as a built-in, automatic, retrying part of every action and assertion, while Selenium treats it as something the test author must explicitly code — that shift is what removes synchronization code from Playwright test scripts entirely.
Mid What are Playwright's actual default timeouts — for actions and for assertions?
30 seconds for actions (click, fill, etc.), configurable via page.set_default_timeout() or a per-call timeout= argument. 5 seconds for web-first assertions (expect()), configured separately. They're two independent values — knowing this precisely (rather than "a few seconds") signals you've actually used the tool, not just watched a tutorial.
Junior What's the difference between to_have_text() and to_contain_text()?
to_have_text() requires the element's full text to match exactly; to_contain_text() is a substring match that passes if the text appears anywhere within. On a narrow locator targeting one label, exact matching is usually right. On a broad locator like body — checking whether text appears anywhere on a page — to_contain_text() is the only sensible option.
Junior How would you test that clicking "Hide" actually hides an element?
Assert visible, click, assert hidden: expect(locator).to_be_visible() → click() → expect(locator).to_be_hidden(). No waits needed between them — both assertions auto-retry, so the DOM changing in between is handled. to_be_hidden() passes whether the element is hidden via CSS or removed from the DOM entirely.
Scenario A colleague fixes a flaky test by adding time.sleep(5) before the assertion. Why is that wrong, and what do you do instead?
It's wrong on both ends. It's too slow when the element appears in 200ms — you've now permanently added 5s to every run of that test. And it's still flaky when a slow CI machine takes 6s. It trades a fast intermittent failure for a slow intermittent failure. The right fix is a web-first assertion (expect(locator).to_be_visible()), which polls and continues the instant the condition holds, and only consumes the full timeout on genuine failure. If a specific step genuinely needs longer, raise that call's timeout= rather than blocking the thread.
Scenario A test passes locally but fails in CI with a timeout on a click. What's your diagnostic sequence?
Auto-waiting means the element failed at least one actionability check for the entire timeout window — so ask which one. Grab a trace (--tracing on) and inspect the DOM snapshot at failure: is the element absent entirely (data/seed differences, slower backend), present but off-screen (smaller CI viewport — a real difference from a local maximized window), present but covered (a cookie banner or overlay that only appears in a fresh CI profile), or present but disabled (an async precondition that hadn't resolved yet)? Each points at a different fix; blanket-raising the timeout usually just makes the failure slower.
Senior Given auto-waiting, is there ever a legitimate reason to wait explicitly?
Yes, for conditions actionability checks don't cover. Actionability is about a specific element's state — it says nothing about, say, a network request having settled, an animation having finished before a visual snapshot, or a background job completing. For those, Playwright provides purpose-built waits (wait_for_load_state, wait_for_response, expect_download, locator.wait_for(state=...)). The rule isn't "never wait" — it's "never sleep a fixed duration." Wait on a condition, not on the clock.
Senior Playwright checks that an element "receives events." What real bug class does that catch?
Elements that are visually present and enabled but covered by something else at the click point — a modal overlay, a sticky header, a cookie banner, a toast notification. Playwright hit-tests the target point and confirms the click would actually reach that element rather than the thing on top of it. Without that check (Selenium's default position), the click silently lands on the overlay: the test reports a successful click, no exception is raised, and it fails confusingly several steps later. It converts a misleading downstream failure into a precise one at the real point of breakage.

Watch out The course gives the global timeout as roughly "7 to 10 seconds," stated informally ("I think") rather than cited from documentation — that was a guess, not a fact. The real defaults (see the supplement box above): 30s for actions, 5s for assertions, and they're independently configurable. Use the real numbers in an interview, not the video's estimate.
