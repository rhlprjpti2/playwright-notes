Lists & Tuples

Lists are the workhorse collection in almost every automation script — building up rows from a table, collecting failed assertions, batching test data. Tuples look similar but exist for a different reason entirely.

Creating & indexing

items = ["login", "checkout", "search"]
items[0]        # "login"
items[-1]       # "search"  — negative index counts from the end
len(items)      # 3

Negative indexing is idiomatic Python — items[-1] for "the last one" reads better than items[len(items) - 1], and it's used constantly when parsing scraped or split text (see the URL-slicing example on String Methods).

Slicing

The full slice syntax is list[start:stop:step] — every part is optional, and stop is exclusive.

ExpressionResultMeaning
items[1:3]["checkout", "search"]index 1 up to (not including) 3
items[:2]["login", "checkout"]from the start
items[1:]["checkout", "search"]to the end
items[::-1]["search", "checkout", "login"]step -1 reverses the whole list
items[:]a new list, same elementsshallow copy — see the trap section below

Unlike indexing a single element, slicing never raises an IndexError for an out-of-range boundary — items[1:100] just returns whatever exists from index 1 onward. Useful, but it also means a typo'd slice fails silently instead of loudly.

append() vs extend() — the interview classic items.append([1, 2]) adds one element that is itself a list — len(items) grows by 1. items.extend([1, 2]) adds each element individually — len(items) grows by 2. Mixing these up is one of the most common real bugs in list-building code, not just an interview trivia question.
a = [1, 2]; a.append([3, 4]) — what is len(a)?

List comprehensions

A list comprehension builds a new list from an existing iterable in one expression — idiomatic Python prefers it over a manual for loop with .append() when the logic is simple enough to read in one line.

# Manual loop
failed = []
for result in test_results:
    if result.status == "failed":
        failed.append(result.name)

# Equivalent comprehension
failed = [r.name for r in test_results if r.status == "failed"]

The general shape is [expression for item in iterable if condition] — the if is optional. Nested loops work too ([x for row in matrix for x in row] flattens a 2D list), but once a comprehension needs a second nested loop or multiple conditions, most style guides agree it's more readable as a regular loop again.

The shared-reference trap

This is the same aliasing idea from Variables & the Memory Model, but in a form that catches people constantly: multiplying a list containing a mutable object doesn't create independent copies — it creates multiple names pointing at the same inner object.

The fix: build each row independently so each gets its own list object.

# Wrong — 3 references to 1 list
matrix = [[0, 0, 0]] * 3

# Right — a comprehension calls the list literal fresh each time
matrix = [[0, 0, 0] for _ in range(3)]

Why tuples exist

A tuple is written with parentheses — (1, 2, 3) — and behaves like a list except it's immutable: no .append(), no item assignment, no .sort(). That restriction is the entire point, not a missing feature.

Use caseWhy a tuple, specifically
Dictionary keysKeys must be hashable; lists aren't hashable (they're mutable), tuples are — cache[(x, y)] = result works, cache[[x, y]] raises TypeError
Multiple return valuesreturn name, status actually returns a tuple — unpacked at the call site via name, status = get_result()
Fixed-shape recordsAn (x, y) coordinate or (row, col) pair that should never accidentally grow a third element
Function default argumentsImmutable, so it's safe as a default in a way a list default is not — see the mutable-default trap
 
# Packing and unpacking
point = 3, 4                 # packing — parens are optional
x, y = point                 # unpacking
x, *rest = [1, 2, 3, 4]      # star-unpacking: x = 1, rest = [2, 3, 4]

Interview Q&A

Junior What's the practical difference between a list and a tuple?
A list is mutable — you can append, remove, or reorder items after creation. A tuple is immutable — once created, its contents can't change. Beyond that, they behave the same for indexing, slicing, and iteration. The immutability is what makes tuples usable as dictionary keys and set members, where lists would raise TypeError: unhashable type.
Junior What's the difference between .append() and .extend()?
.append(x) adds exactly one item — even if x is itself a list, it gets added as a single nested element. .extend(iterable) adds every item from the iterable individually, growing the list by however many elements the iterable had. a.append([1,2]) makes len(a) grow by 1; a.extend([1,2]) makes it grow by 2.
Mid Why does matrix = [[0, 0]] * 3 produce a bug when you try to mutate one row?
* on a list repeats references, not deep copies — all 3 slots in matrix end up pointing at the exact same inner list object. Mutating matrix[0][0] mutates that shared object, so every row appears to change simultaneously. The fix is [[0, 0] for _ in range(3)], which evaluates the list literal fresh on each iteration, producing 3 independent objects.
Mid Why can a tuple be used as a dict key but a list can't?
Dict keys must be hashable, and Python's rule is that mutable types are unhashable — if a list's contents could change after being used as a key, its hash would change too, corrupting the dict's internal bucket structure. Tuples are immutable, so their hash is stable for their entire lifetime, making them safe as keys (as long as everything inside the tuple is also hashable).
Senior When would you deliberately choose a list comprehension over a plain for loop, and when would you avoid one?
Use one when the transformation is a single clear expression with at most one filter condition — it reads as "build a list of X for each Y where Z" faster than five lines of loop boilerplate, and it's typically a bit faster too since the append calls happen in optimized C rather than Python bytecode. Avoid one once you need a second nested loop, multiple conditions, or a side effect (like logging) per iteration — at that point a comprehension becomes a puzzle to read backward instead of a shortcut, and a plain loop is the more maintainable choice.

Gotchas

Slicing looks safe but silently returns partial results items[2:100] never raises, even though there's no index 100 — it just returns everything from index 2 to the end. A typo'd boundary produces a shorter-than-expected list instead of an error, which can hide bugs in data-parsing code for a long time.
a[:] and list(a) are shallow copies Both create a new outer list, but if the elements themselves are mutable (like nested lists), the inner objects are still shared between the original and the copy — mutating a nested element through the copy still affects the original. Use copy.deepcopy() if you genuinely need independent nested structures.
