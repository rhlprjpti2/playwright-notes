Generators & yield

A pytest fixture using yield for setup/teardown is a generator function. Understanding what yield actually does — pause and resume, not "return multiple times" — explains that pattern and a whole class of memory-efficient code.

The memory problem

Say you need to process a log file with 10 million lines, checking each one for an error pattern. Reading it into a list first means holding all 10 million lines in memory simultaneously — even though at any moment you only actually need the one line you're currently looking at.

# Loads the entire file into memory as a list, all at once
def read_lines_list(path):
    lines = []
    with open(path) as f:
        for line in f:
            lines.append(line)
    return lines

# Yields one line at a time — never holds more than one line in memory
def read_lines_gen(path):
    with open(path) as f:
        for line in f:
            yield line

Both functions look almost identical to call — for line in read_lines_gen(path): works exactly like iterating a list. The difference is entirely about when each line gets produced and how much memory is held at once, which ties directly back to the object model on Variables & the Memory Model: a list holds references to every element simultaneously; a generator holds a paused execution frame and produces one value at a time, on demand.

yield vs return

return ends a function permanently, handing back one value. yield pauses the function, hands back one value, and — critically — remembers exactly where it left off, ready to resume from that exact point the next time a value is requested.

def count_up_to(n):
    i = 1
    while i <= n:
        yield i
        i += 1        # this line only runs when the generator is resumed

gen = count_up_to(3)
next(gen)   # 1  — runs until the first yield, then pauses
next(gen)   # 2  — resumes right after yield, runs i += 1, loops, yields again
next(gen)   # 3
next(gen)   # raises StopIteration — the while condition is now False

Calling count_up_to(3) does not run any of the function's code yet — it immediately returns a generator object. The body only starts executing on the first next() call, and only runs as far as the next yield before pausing again. This lazy, on-demand execution is the entire mechanism behind the memory savings above.

Generator expressions

The same syntax as a list comprehension, but with parentheses instead of square brackets — and the same lazy, one-at-a-time evaluation as a yield-based generator function.

squares_list = [x * x for x in range(1000000)]   # builds all 1,000,000 values now
squares_gen  = (x * x for x in range(1000000))    # builds nothing yet — lazy

sum(x * x for x in range(1000000))   # no brackets needed when it's a sole function argument

For anything that gets consumed once in a loop or passed straight into sum()/max()/any(), a generator expression is the more memory-efficient choice by default — there's rarely a reason to materialize the full list first if nothing needs random access or a second pass over it.

The iterator protocol

A for loop over any iterable — a list, a generator, a file, a dict — is secretly doing the same two-method dance every time: calling iter() once to get an iterator, then calling next() repeatedly until StopIteration is raised.

items = [1, 2, 3]
it = iter(items)
next(it)   # 1
next(it)   # 2
next(it)   # 3
next(it)   # raises StopIteration

# This is exactly what `for x in items:` does under the hood

A generator (whether from a yield function or a generator expression) already satisfies this protocol automatically — it's an object with its own __next__ built in, which is why it can be looped over directly without any extra wrapping.

Why pytest fixtures use yield

The setup/teardown pattern on Pytest Fixtures & Fundamentals is a generator function used for its pause-and-resume behavior, not for producing a sequence of values.

@pytest.fixture
def page(browser):
    page = browser.new_page()
    yield page          # pytest resumes the test here, using this value
    page.close()         # this runs only after the test finishes — teardown

Pytest calls next() on the fixture generator once to run the setup code and get the yielded page object, hands that to the test, runs the test, and then calls next() again afterward — which resumes the generator right after the yield line and runs the teardown code. The exact same pause/resume mechanism as the log-file example above, just used for "do setup, hand off control, do cleanup" instead of "produce a sequence of values."

Interview Q&A

Junior What's the core difference between yield and return?
return exits a function permanently and hands back one value. yield pauses the function at that exact line, hands back one value, and preserves all local state so execution can resume from right after the yield the next time a value is requested. A function containing yield anywhere in its body becomes a generator function — calling it returns a generator object rather than running the body immediately.
Mid Why would you use a generator instead of returning a list?
Memory. A list holds every element in memory simultaneously, which is fine for small collections but wasteful or impossible for huge or unbounded sequences (a large file's lines, an infinite counter, a paginated API being consumed page by page). A generator produces one value at a time, on demand, so memory use stays constant regardless of how many items get produced in total — the tradeoff is that a generator can only be iterated once and doesn't support indexing or len().
Mid What does calling a generator function actually do, versus calling a regular function?
Calling a regular function runs its body immediately and returns the result. Calling a generator function (one containing yield) runs none of the body — it immediately returns a generator object. The body only begins executing on the first call to next() (or the first iteration of a for loop over it), and each subsequent next() resumes execution from directly after the last yield, rather than starting over.
Senior Explain what's actually happening when a pytest fixture uses yield instead of return for setup/teardown.
The fixture function is a generator. Pytest calls next() on it once before the test runs — this executes the setup code and pauses at the yield line, and the yielded value becomes what gets injected into the test as the fixture's value. The test then runs using that value. Once the test finishes (pass or fail), pytest calls next() again, which resumes the generator immediately after the yield and runs whatever teardown code follows — closing a browser, deleting test data, etc. This guarantees teardown runs even though it's written after the point where control was handed to the test, because the generator's paused frame kept that "resume point" alive the whole time the test was executing.

Gotchas

A generator can only be iterated once Once exhausted (StopIteration raised), a generator is permanently spent — looping over it again yields nothing, silently. A list can be iterated as many times as you want; a generator can't. If you need to iterate the same data twice, either store it as a list or call the generator function again to get a fresh generator object.
len() doesn't work on a generator A generator doesn't know its total length in advance — it only knows how to produce the next value — so len(my_generator) raises TypeError. If you need a count, either consume it into a list first or track a counter manually while iterating.
