Pytest Fixtures & Fundamentals

The single most interview-relevant Pytest topic before Playwright even enters the picture: how tests get discovered, how fixtures work, why they don't run automatically like JUnit/TestNG hooks, and every option @pytest.fixture actually accepts — scope, params, autouse, ids, name — plus conftest.py and the yield-based setup/teardown pattern. Play with the simulators below — don't just read past them.

Concept

Pytest is Python's testing framework/engine — the direct equivalent of JUnit for Java. Playwright's Python tests are written and run on top of Pytest, which is why Pytest fundamentals are a prerequisite, not an optional side topic.

Fixtures are Pytest's mechanism for reusable setup code shared across multiple tests — think "reusable pre-work," like spinning up a browser instance before every test that needs one.

The decorator, in full

@pytest.fixture works with no arguments at all — that's every example so far on this page. But it also accepts five keyword arguments that change how the fixture behaves, and each one is fair game in an interview. This section is the map; the next few sections each zoom into one entry.

OptionDefaultChanges
scope"function"How often the fixture body actually runs — covered in Fixture scopes
paramsNoneReruns every test that uses this fixture once per value — covered in Parametrized fixtures
autouseFalseRuns for every test in scope without being named as an argument — covered in autouse
idsNoneCustom readable names for each parametrized run, instead of Pytest's auto-generated [0], [1], ...
namethe function's own nameLets tests request the fixture under a different argument name than the function is defined with
 
# ids and name in practice
@pytest.fixture(params=["chromium", "firefox"], ids=["chrome", "ff"])
def browser_name(request):
    return request.param
# without ids: test names show test_x[chromium], test_x[firefox]
# with ids:    test names show test_x[chrome], test_x[ff]

@pytest.fixture(name="page")
def _page_impl(browser):
    return browser.new_page()
# tests request it as `page`, not `_page_impl` — useful when the function
# name would otherwise shadow a variable, or you want a shorter public name

Test discovery rules

  • A function is only treated as a test if its name is prefixed or postfixed with test (e.g. test_initial_check). Without that keyword, it's just a plain function — Pytest won't touch it, no matter what's inside.
  • A file is only scanned by the pytest CLI command if its filename also starts with test (e.g. test_validation.py). Running the bare pytest command walks the current directory and only picks up files matching that naming rule.
  • The -s flag on the CLI (pytest -s) shows print() output in the console — without it, print statements are suppressed from the run output.

Running & selecting tests

Beyond running a whole directory with a bare pytest, you can target specific tests or skip/tag them for selective runs — all relevant later when a CI/CD pipeline needs to trigger specific subsets.

  • Run one file: pytest test_validation.py — runs only that file, ignoring every other test file in the directory.
  • Run one function: pytest test_validation.py::test_initial_check — the double-colon :: separates the file from the specific test function name.
  • Skip a test: @pytest.mark.skip above a test function — Pytest will skip it during any run and report it as "skipped" rather than pass/fail.
  • Tag/mark tests: @pytest.mark.smoke (any custom name) applied to multiple tests, then run only that subset with pytest -m smoke. Tests without the mark are reported as "deselected." This is the Pytest equivalent of Cucumber tags or TestNG groups.
Shared prefix Both skipping and custom tagging use the same @pytest.mark.* namespace — .skip is really just a built-in mark, structurally no different from a custom one like .smoke.

Fixture linkage & resolution

Unlike Java's TestNG/JUnit @BeforeTest, which runs automatically for every test with no explicit reference, a Pytest fixture only executes if a test names it as an argument. Defining @pytest.fixture alone does nothing until something links to it.

You write @pytest.fixture above def pre_work(): but no test function takes pre_work as an argument. What happens when you run the suite?
One exception coming up autouse=True is the one case where a fixture runs without being named as a test argument at all — covered in full in autouse below.

Fixture scopes

Scope controls how often a fixture actually runs, independent of how many tests reference it. Default scope is function.

ScopeRunsNotes
functionBefore every test that references itDefault scope if none is specified
classOnce per test classSame idea as module scope, but for tests grouped in a class instead of a file
moduleOnce per test fileEven if 5 tests in that file reference it, it runs only once at the start
sessionOnce per full test run, across every fileOnly observable when running the whole suite together — running a single file in isolation, Pytest can't tell it apart from module scope
Practical use Session scope is the natural choice for something expensive you want created exactly once across an entire run — e.g. launching one browser instance reused by all 30-40 tests in a framework, instead of relaunching per test or per file.

Parametrized fixtures

params is the option that changes behavior the most: instead of running once, the fixture runs once per value in the list — and every test that uses it gets re-run once per value too, each with a different request.param.

@pytest.fixture(params=["chromium", "firefox", "webkit"])
def browser_name(request):
    return request.param   # whichever value this particular run is on

def test_login(browser_name):
    print(f"running on {browser_name}")
    # this one test function becomes THREE test runs — one per browser
A fixture has params=["a", "b", "c"] and one test uses it. How many results show up in the test report?
Where the value actually comes from request is a special built-in fixture — ask for it as a parameter and Pytest hands you an object describing the current test run, including request.param for whichever value this particular run is on. It only carries a value when the fixture is parametrized; using request.param on a non-parametrized fixture raises an error.

autouse

Every fixture on this page so far only runs because a test named it as an argument. autouse=True is the one exception — the fixture runs for every test in its scope, whether or not anything asks for it by name.

Use it sparingly A test's fixture arguments are its documented dependencies — anyone reading def test_login(page, api_client): knows exactly what ran before it. An autouse fixture is invisible from every test signature it affects, so overusing it makes tests harder to reason about. Reserve it for things every test genuinely needs regardless of whether it asks — global logging, a session-wide browser launch, resetting shared state between tests.

conftest.py

conftest.py is a specifically-named file (the name is fixed, not customizable) that Pytest automatically checks for shared fixtures. Resolution order: Pytest first checks the test's own file for the fixture; if it isn't defined there, Pytest falls back to conftest.py in the same directory.

Purpose: instead of repeating the same setup fixture (browser launch, API client setup, etc.) in every test file, define it once in conftest.py and every test file in that directory can reference it by name.

Setup/teardown with yield

The yield keyword splits a single fixture into a setup phase (code before yield) and a teardown phase (code after yield) — Pytest's equivalent of before/after hooks, without needing two separate functions. Step through the actual execution order below instead of just reading about it.

  • Everything before yield = setup — connections, logins, browser launches.
  • Everything after yield = teardown — closing connections, closing the browser, deleting cookies.
  • One fixture, split by yield, gives you both — no separate teardown function needed.
  • yield "fail" hands data to the test exactly like return would — it just also gives you a teardown phase afterward, which is why the test can assert against it.

Returning data from fixtures

A fixture isn't limited to running setup actions — it can also return data that the test then receives through the fixture argument. This is how framework-level fixtures typically supply test data: login credentials, tokens, IDs, etc., defined centrally rather than hardcoded per test.

1 @pytest.fixture 2 def pre_work(): 3   print("setup") 4   return "fail" 5 6 def test_initial_check(pre_work): 7   # pre_work now holds whatever was returned

Interview Q&A

Mid Does a Pytest fixture run automatically, like JUnit's @BeforeTest or TestNG's before-hooks?
No — this is a common trip-up for people coming from Java. A Pytest fixture only executes when a test function explicitly names it as an argument. Defining @pytest.fixture alone does nothing on its own; without the linkage, the fixture body never runs.
Junior Explain the four fixture scopes and how they differ.
function (default) runs before every test that references it. class runs once per test class. module runs once per test file, no matter how many tests in that file use it. session runs exactly once across the entire test run, shared across all files — but this is only observable when running the full suite, since running one file in isolation looks identical to module scope.
Junior What is conftest.py and why does it need that exact filename?
It's a specially-recognized file Pytest automatically checks for fixture definitions not found in a test's own file. The filename is fixed — Pytest looks for it by that exact name in the same directory as the tests. It's used to centralize fixtures shared across multiple test files instead of duplicating them.
Mid How do you implement both setup and teardown in a single fixture?
Use the yield keyword. Code before yield runs as setup; Pytest then pauses the fixture, runs the test, and once the test completes, resumes the fixture from the line after yield as teardown — all inside one function, no separate before/after methods needed.
Junior How do you run a single test function from the command line, and how do you run only a tagged subset?
Target a single function with the double-colon syntax: pytest test_file.py::test_function_name. For a tagged subset, mark tests with @pytest.mark.<tagname> (e.g. @pytest.mark.smoke) and run pytest -m smoke — tests without that mark are skipped as "deselected." This is Pytest's equivalent of Cucumber tags or TestNG groups.
Junior Can a fixture provide test data, not just perform setup actions?
Yes. A fixture can return a value (or yield one), and that value becomes accessible to the test through the fixture argument — commonly used to centrally supply data like credentials or tokens rather than hardcoding them per test.
Mid What is autouse=True and when is it appropriate?
It makes a fixture run for every test in its scope without any test naming it as an argument — the one exception to the normal linkage rule. Appropriate for genuinely universal concerns like global logging setup or a session-wide browser launch. Overusing it hurts readability, because a test's dependencies become invisible from its signature: someone reading the test can no longer tell what ran before it.
Mid What does the params argument on @pytest.fixture actually do?
It reruns every test that uses the fixture once per value in the list — not just changes the value once. @pytest.fixture(params=["chromium", "firefox", "webkit"]) turns one test function into three independent test runs, each with a different request.param, each reported separately in the results. This is how cross-browser test matrices are typically built without hand-writing three near-identical test functions.
Junior Inside a parametrized fixture, how does the fixture actually access the current value?
Through the built-in request fixture — declare it as a parameter and read request.param. It only holds a value when the fixture is parametrized; calling it on a fixture with no params raises an error, since there's no value to hand back.
Scenario A parametrized fixture with 3 values is used by 2 different tests. How many total test runs does that produce?
6. Parametrization multiplies — each of the 2 tests gets re-run once per value in the fixture's params list, independently. This is worth doing the arithmetic on explicitly in an interview, since it's a common source of "why did my suite suddenly report way more tests than I wrote" surprise once params get combined with multiple consuming tests, or worse, multiple parametrized fixtures on the same test (which multiplies further, not adds).
Mid Can one fixture depend on another? How does Pytest resolve the chain?
Yes — a fixture declares another fixture as a parameter exactly like a test does. Pytest builds the full dependency graph and instantiates them in order, caching each according to its scope. So a session-scoped fixture consumed by three function-scoped fixtures is still created only once.
Scenario A fixture has scope="session", but you observe it running before every single test. What are the likely causes?
Two common ones. First: it's being requested by a narrower-scoped fixture in a way that forces re-creation, or you're misreading output that's actually showing a different function-scoped fixture. Second and more likely: you're running one file at a time, where session and module scope are behaviourally indistinguishable — the difference only appears across a multi-file run. Verify by running the full suite with -s and counting the setup prints. Also confirm the argument is spelled scope="session" exactly; a typo silently falls back to the default function scope.
Senior Teardown code after yield — does it still run if the test fails? What if the setup itself raises?
If the test fails, teardown after yield still runs — that's the main advantage over cleanup written inline at the end of a test, which gets skipped on exception. If the fixture's own setup raises before reaching yield, the teardown half never executes, because execution never got there — so anything already allocated at that point can leak. For setup that acquires several resources, either split into separate fixtures (each with its own teardown) or guard with try/finally inside the fixture.
Senior When is session-scoped browser reuse the wrong choice?
When tests can contaminate each other through shared browser state — cookies, localStorage, service workers, or an authenticated session leaking from one test into the next and creating order-dependent passes. The usual resolution isn't abandoning the session-scoped browser (which is expensive to launch), but giving each test its own context from that shared browser: cheap to create and fully isolated. Session-scoped browser + function-scoped context is the standard trade-off.

Gotchas

Watch out Module scope and session scope can look identical if you only ever run one file at a time — both appear to run "once." The difference only becomes observable when running the full suite across multiple files together.
Watch out A fixture must be referenced by name as an argument to activate — simply having @pytest.fixture above a function is not enough for it to execute.
Watch out params multiplies, it doesn't add. Two parametrized fixtures on the same test (3 values and 4 values) produce 12 runs, not 7 — every combination of both, not a run per fixture. A suite's test count can balloon fast once more than one parametrized fixture is in play.
Interview framing If asked to compare Pytest fixtures to JUnit/TestNG hooks, the sharpest answer isn't "they're similar" — it's naming the one real structural difference: explicit linkage (argument-based) vs. automatic annotation-based execution.
