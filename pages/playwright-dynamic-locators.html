Dynamic Locators, Filtering & Scoped Search

The pattern for writing scripts that don't break when a page's item order changes: scan everything matching a tag, filter down to the one that matches your data, then search only inside it. Demonstrated with a product-cart scenario (add "iPhone X" and "Nokia Edge" to cart, by name — not by position).

Concept

Hardcoding "click the first card" or "click the third button" is fragile — if the page's display order changes (sorting, re-ranking, a new item added), an index-based script breaks even though the target item still exists. The resilient approach: locate every matching element, filter down to the one whose content matches your target data, then scope any further search to inside that specific element.

The scan-and-filter pattern

watch "iPhone X" get resolved to one button — click to run

Worked example

Goal: find the products named "iPhone X" and "Nokia Edge" wherever they currently sit on the page, add each to the cart, then check out.

iphone_product = page.locator("app-card").filter(has_text="iPhone X")
iphone_product.get_by_role("button").click()   # only one button exists inside this scoped card

nokia_product = page.locator("app-card").filter(has_text="Nokia Edge")
nokia_product.get_by_role("button").click()

page.get_by_text("Checkout").click()   # partial text match is enough

Note the scoping: page.get_by_role("button") would search the entire page and likely match many buttons. iphone_product.get_by_role("button") only searches within the already-filtered card, so it uniquely resolves without needing a name= filter — because the search space itself was already narrowed down to one card.

Beyond this video — other filter and index options The video uses has_text only. Also available: .filter(has_not_text="Out of stock") excludes matches containing that text; .filter(has=page.get_by_role("button", name="Sold Out")) filters by whether a matched element contains another locator, not just text. Separately, if you deliberately do want a specific position rather than filtering by content, .nth(0), .first, and .last pick by index — the exact "fragile" approach this page argues against by default, but occasionally the right tool when position genuinely is the thing under test (e.g. "the most recent entry").

Asserting on count

To verify how many elements a locator ultimately matched (e.g. confirming exactly 2 items landed in the cart), use the to_have_count web-first assertion:

from playwright.sync_api import expect

expect(page.locator(".media-body")).to_have_count(2)

Interview Q&A

Junior Why scan-and-filter instead of clicking an element at a fixed index?
Resilience. If the page's display order changes — items re-sorted, a new item inserted — an index-based script targets the wrong element or breaks entirely. A filter-by-content script finds the correct element regardless of its position on the page.
Mid What's the difference between `page.locator(...).get_by_role(...)` and `product_locator.get_by_role(...)`?
Scope. The first searches the entire page for that role, which can return many matches. The second searches only within the previously-located element (`product_locator`), so it can resolve uniquely without further filtering — because the search space was already narrowed.
Junior How do you assert on the number of elements a locator matched?
expect(locator).to_have_count(n) — a web-first assertion, so it auto-retries like other Playwright assertions rather than checking the count exactly once immediately.
Mid What's the difference between get_by_role's `name=` filter and a separate `.filter(has_text=...)` call?
name= is bundled directly into get_by_role and specifically matches the element's accessible name. .filter() is a separate, more general-purpose chained method usable on any locator (not just role-based ones), and can match on text content via has_text (there's also has_text/has_not_text/has variants for different filter conditions).
Mid Are Playwright locators evaluated when you create them?
No — locators are lazy. Creating one just describes how to find an element; the DOM query runs at the moment you act or assert on it, and re-runs on each auto-wait retry. That's why a locator stored in a variable still works after the page updates, and why locators don't go stale the way a Selenium WebElement reference does.
Scenario You must click "Delete" on the row for user "jsmith" in a table where rows load in unpredictable order. How do you write it?
Filter to the row by its content, then scope the button search inside that row: page.get_by_role("row").filter(has_text="jsmith").get_by_role("button", name="Delete").click(). The row is identified by the data that makes it unique, not its index, and the Delete button is found within that row — so it can't accidentally hit another row's Delete even though every row has one. This is the canonical shape of this whole pattern.
Senior When is using .nth() or .first actually the correct choice rather than a smell?
When position itself is the thing under test, not an incidental detail. Examples: asserting that a "sort by newest" control genuinely puts the newest item first, verifying a top-ranked search result, or checking pagination boundaries. The distinction is intent — .first is legitimate when your assertion is about ordering, and a smell when you're just using position as a lazy proxy for identity. A useful tell: if reordering the data should keep the test passing, filtering by content is right; if reordering should fail the test, position is right.

Gotchas

Watch out Hardcoding an index ("the first card," "the third button") is exactly the anti-pattern this technique exists to avoid — it's fragile the moment content order changes, even though nothing about the target element itself changed.
