Network Interception & Session Storage

Two edge cases that are painful to set up for real — an account with zero orders, someone else's order ID — and one that's slow to repeat every test: logging in through the UI. page.route() solves the first two by tweaking traffic in flight; page.add_init_script() solves the third by planting a login token before the page ever loads. Neither one touches real test data or a real login form.

Why mock the network at all

Some scenarios are painful to set up with real data:

  • Empty state — to see "you have no orders," you'd otherwise have to delete every real order first (or maintain a dedicated empty test account) just to test one message.
  • Security edge cases — testing "you can't view someone else's order" means getting your hands on another account's real order ID, which usually isn't practical in an automated suite.

page.route(url_pattern, handler) intercepts matching network traffic before it completes, the same way page.on("dialog", ...) intercepts dialogs and expect_popup() intercepts new windows — register interest before the trigger, then react when it fires. The difference here is what you can do once you've intercepted it: fake the response entirely, or let the request through with something changed.

Mocking a response: route.fulfill()

The scenario: an account has real orders, but the test needs to verify the empty-state message — without deleting anything. Register a route on the orders API call, and when it fires, answer it yourself instead of letting it reach the server:

def handle_orders_route(route):
    fake_empty_response = {
        "orders": [],
        "message": "You have no orders to show at this time."
    }
    route.fulfill(status=200, json=fake_empty_response)

def test_empty_orders_message(page):
    page.goto(BASE_URL)
    page.get_by_label("Username").fill("test_user")
    page.get_by_label("Password").fill("...")
    page.get_by_role("button", name="Login").click()

    # Regex — the customer ID segment changes per account, "*" covers it
    page.route("**/customers/*/orders", handle_orders_route)

    page.get_by_role("link", name="Orders").click()
    message = page.locator(".empty-orders").text_content()
    assert message == "You have no orders to show at this time."

route.fulfill() answers the request locally — the real backend never sees it at all. The browser gets exactly the JSON handed to it, renders accordingly, and the actual account's real orders are never touched.

The account still has its real orders after the test Nothing was deleted and no test data was swapped — only the one intercepted response was faked. The next real page load (outside the mocked route) sees the genuine orders again.

Mocking a request: route.continue_()

The scenario is reversed: instead of faking what comes back, this time the outgoing request itself needs to change before it reaches the server. A user views their own order, and the test needs to prove that swapping in another account's order ID doesn't leak that data:

def handle_order_id_swap(route):
    other_account_order_url = "https://shop.example.com/api/orders?id=OTHER-ACCT-ID"
    route.continue_(url=other_account_order_url)

def test_cannot_view_other_accounts_order(page):
    page.goto(BASE_URL)
    # ...login as this test's own account...
    page.get_by_role("link", name="Orders").click()

    page.route("**/orders*id=*", handle_order_id_swap)
    page.get_by_role("button", name="View").first.click()

    message = page.locator(".error-message").text_content()
    assert message == "You are not authorized to view this order."

route.continue_() lets the request proceed to a real server — just with something about it changed first (here, the URL; it can also override the method, headers, or body). This is a genuine network call, unlike fulfill(). The assertion proves the backend itself rejects the mismatched ID, which is the actual security property under test.

Python note: the trailing underscore is required continue is a reserved keyword in Python, so the method is named continue_(), not continue(). Easy to typo under pressure in an interview or a live coding round.

fulfill() vs. continue_()

These get mixed up because both start with the identical setup — page.route(pattern, handler) — and only diverge inside the handler. The distinction is the single most interview-relevant fact on this page:

route.fulfill(...)route.continue_(...)
Does a real network call happen?No — answered locallyYes — proceeds to a real server
What you controlThe entire response — status, headers, bodyThe outgoing request — URL, method, headers, post data

Route API reference

MemberWhat it does
route.fulfill(status=, json=, headers=)Answers the request locally — no real network call is made.
route.continue_(url=, method=, headers=, post_data=)Forwards the request to a real server, optionally modified first.
route.abort()Fails the request outright — simulates a network error / offline condition.
route.requestThe intercepted request — .url, .method, .headers, .post_data.
page.unroute(pattern)Removes a previously registered handler for that pattern.

The pattern passed to page.route() can be a glob string ("**/orders*" — ** matches any number of path segments, * matches within one), a regular expression, or a predicate function for anything more specific than either can express.

Bypassing login with local storage

A separate problem: most tests need to be logged in, and re-running a real login form on every single test adds seconds of setup, repeated hundreds of times across a suite. Many apps store their auth token in the browser's localStorage after login — if that token can be planted before the page loads, the app treats the session as already authenticated and the login form never appears at all.

def test_orders_visible_without_logging_in(page):
    token = api_utils.get_token(playwright, username="test_user", password="...")

    page.add_init_script(f"""
        window.localStorage.setItem('token', '{token}');
    """)

    page.goto(f"{BASE_URL}/client")   # lands straight past the login screen
    page.get_by_role("button", name="Orders").click()
    expect(page.get_by_text("Order History")).to_be_visible()

page.add_init_script() registers JavaScript that runs before any of the page's own scripts, on every document the page navigates to. Setting the token there means it's already sitting in localStorage the instant the app's own startup code checks for it — which is exactly what a real login would have left behind, just without spending any time on the login form itself.

Where does the token actually come from? The script only plants the token — it doesn't generate one. A real one has to be obtained first, typically via a direct API login call (see API Testing & Assertion Validation) rather than the UI. The whole point is skipping the UI form, not skipping authentication itself.

The Playwright-native alternative: storage_state

Hand-writing a localStorage.setItem(...) script works, but it's re-deriving something Playwright already does natively. A browser context can be created directly from a previously captured session:

# Capture once, from an already-authenticated context
state = context.storage_state()   # cookies + localStorage, serializable

# Reuse — a brand-new context that starts already logged in
authed_context = browser.new_context(storage_state=state)
page = authed_context.new_page()
page.goto(f"{BASE_URL}/client")   # no login screen, no add_init_script needed
Beyond this video — storage_state is the built-in version of the same trick storage_state captures cookies as well as localStorage and sessionStorage in one object supplied directly to new_context() — no manual JavaScript string, and no risk of a typo in a hand-written setItem call. It's usually the better default; add_init_script() is still the right tool when something more custom than "restore an existing session" is needed — injecting a feature flag, a mocked Date, or any other pre-navigation script.

Interview Q&A

Junior What does page.route() do?
It registers a handler for network requests matching a URL pattern (glob, regex, or predicate). When a matching request fires, Playwright routes it to the handler instead of letting it proceed normally — the handler then decides what happens: answer it locally with fulfill(), forward it (optionally modified) with continue_(), or block it with abort().
Mid What's the difference between route.fulfill() and route.continue_()?
fulfill() answers the request entirely locally — no real network call happens, and you control the whole response (status, headers, body). continue_() lets the request proceed to a real server, optionally with something changed first (URL, method, headers, body). fulfill() tests how the frontend reacts to a given response; continue_() tests how the backend reacts to a given request.
Mid Why would a test mock a response instead of just using real test data?
Some states are impractical to produce with real data on demand — an account with literally zero orders, a specific error response, a slow network. Rather than maintaining dedicated accounts or destructively deleting real records just to hit one UI state, the response is faked for that one request only; the real backend and real data are never touched.
Mid How would you test that a user can't view another account's order by tampering with the order ID?
Register a route on the order-details request, and inside the handler use route.continue_(url=...) to swap in another account's order ID before the request reaches the server. Assert that the app shows an authorization error rather than the other account's data. Because continue_() still sends a real request, the assertion is proving the backend itself enforces the check — not just that the frontend would display an error if told to.
Mid Why does page.add_init_script() have to be called before page.goto()?
It registers a script to run on future navigations — it doesn't retroactively run on a page that's already loaded. Called after goto(), the app's own startup JavaScript (which checks localStorage for a token) would already have executed and found nothing, so the login screen would still appear. This is the same "register before the trigger" ordering rule that governs dialog handlers and route handlers elsewhere in Playwright.
Senior Would you use add_init_script() or storage_state to skip a login screen, and why?
storage_state for the common case — it captures cookies, localStorage, and sessionStorage together from an already-authenticated context and restores all of it in one call to new_context(storage_state=...), with no hand-written JavaScript to get subtly wrong. add_init_script() is the right tool for something storage_state can't express — injecting a feature flag, mocking Date, or any other pre-navigation script that isn't just "restore a session that already existed."
Senior Is mocking the network the same thing as API testing?
No, and conflating them is a common mistake. API testing (APIRequestContext) sends a real request and validates the real backend's real response — see API Testing & Assertion Validation. Route interception with fulfill() never contacts the real backend at all — it's for controlling what the frontend receives, useful for UI states the real backend won't reliably reproduce on demand. continue_() sits in between: a real request still goes out, just with something intentionally altered first.

Gotchas

A route handler stays active for every matching request Once registered, page.route(pattern, handler) applies to every subsequent request matching that pattern for the rest of the page's lifetime — the same "register once, applies to everything after" behavior as dialog handlers. Use page.unroute(pattern) if a later step needs the real, un-mocked network call again.
The route pattern needs to actually match the real request A pattern that's too narrow (hardcoding a dynamic customer or order ID instead of wildcarding it) silently never fires, and the test proceeds against the real, un-mocked network — often failing later in a confusing way that looks unrelated to the routing at all.
Registering the route too late misses the request Same ordering rule as dialogs and popups: the route has to be armed before the action that triggers the request (the click on "Orders," in this page's examples), not after.
fulfill() needs a real body Calling route.fulfill() with no body/json at all sends an empty response, which is rarely what a JSON-consuming frontend expects — it typically fails to parse rather than rendering a sensible empty state.
