Functions Deep Dive

def is easy. What separates a working function signature from one that's actually pleasant to call — *args, **kwargs, keyword-only params — and the scope rules that decide which variable a name inside a function actually refers to, is less obvious.

Parameter types

def run_test(name, browser="chromium", headless=True):
    ...

run_test("test_login")                          # browser="chromium", headless=True
run_test("test_login", "firefox")                # positional
run_test("test_login", browser="firefox")        # keyword — same effect, clearer at the call site
run_test("test_login", headless=False)           # skip browser, target headless directly by name

Default values are evaluated exactly once, at function-definition time — not on every call. That's harmless for immutable defaults like True or "chromium" above, but genuinely dangerous for mutable ones; see the mutable-default-argument trap if you haven't already.

*args and **kwargs

*args collects any extra positional arguments into a tuple; **kwargs collects any extra keyword arguments into a dict. Neither name is special — * and ** are what matter, the names are just convention.

def log_step(action, *args, **kwargs):
    print(action, args, kwargs)

log_step("click", "#submit-button", retries=3, timeout=5000)
# action = "click"
# args   = ("#submit-button",)
# kwargs = {"retries": 3, "timeout": 5000}

The reverse operation — unpacking a list/dict into a call — uses the same symbols on the caller's side:

coords = (10, 20)
move_to(*coords)          # same as move_to(10, 20)

opts = {"timeout": 5000, "force": True}
element.click(**opts)      # same as element.click(timeout=5000, force=True)

Positional-only and keyword-only parameters

Two lesser-known markers in a function signature restrict how a parameter can be passed — useful for API design where you want to lock down the call style.

def connect(host, port, /, *, timeout=30):
    ...
    # host, port  — before the /  → positional-ONLY, can't use host=
    # timeout     — after the *   → keyword-ONLY, must use timeout=

connect("localhost", 8080, timeout=10)   # ✓ correct
connect(host="localhost", port=8080)     # ✗ TypeError — host/port are positional-only
connect("localhost", 8080, 10)           # ✗ TypeError — timeout is keyword-only

You'll see this constantly in the standard library's own function signatures (check any built-in's help() output) even if you rarely write / yourself — recognizing it is the practical skill.

The LEGB scope rule

When Python resolves a name inside a function, it checks four scopes in this exact order, stopping at the first match: Local → Enclosing (an outer function, for nested functions) → Global (module level) → Built-in (len, print, etc).

x = "global"

def outer():
    x = "enclosing"
    def inner():
        x = "local"
        print(x)      # "local" — found immediately, search stops
    inner()

outer()   # prints "local"

Assigning to a name inside a function makes Python treat it as local for the entire function body, even before the assignment line — reading it earlier in the function raises UnboundLocalError rather than falling back to the global. To explicitly modify a name from an outer scope, use global or nonlocal:

counter = 0
def increment():
    global counter
    counter += 1   # without `global`, this line alone would raise UnboundLocalError

Closures & the late-binding trap

A closure is an inner function that remembers variables from its enclosing scope even after that outer function has returned. The catch: it remembers the variable, not the value at closure-creation time — and that variable keeps changing until the loop that created it finishes.

The fix forces evaluation at creation time by capturing the current value as a default argument, which — unlike the closure lookup — is evaluated once, immediately:

# Fixed — default arg captures the value of i at that iteration
makers = [lambda i=i: i for i in range(3)]
[m() for m in makers]   # [0, 1, 2]

Functions as values

Functions are ordinary objects in Python — assignable to variables, passable as arguments, returnable from other functions. This is what makes patterns like custom sort keys and decorators possible at all.

results = [{"name": "a", "duration": 3.2}, {"name": "b", "duration": 1.1}]
results.sort(key=lambda r: r["duration"])   # a function passed as an argument

def retry(fn, times=3):
    for _ in range(times):
        try:
            return fn()
        except Exception:
            continue
    raise RuntimeError("all retries failed")

retry(lambda: page.click("#flaky-button"))

A lambda is just an anonymous, single-expression function — anything a lambda can do, a regular def can also do, and once the logic needs more than one expression or a docstring, def is the better (and often required) choice.

Interview Q&A

Junior What do *args and **kwargs actually mean?
*args collects any extra positional arguments a function receives into a tuple; **kwargs collects any extra keyword arguments into a dict. They let a function accept a variable, unknown-in-advance number of arguments. The names args/kwargs are just convention — the * and ** symbols are what actually matter to Python.
Mid What's the LEGB rule?
It's the order Python searches scopes to resolve a variable name: Local (inside the current function) → Enclosing (an outer function, for nested/closure functions) → Global (module level) → Built-in (Python's built-in names like len). Python stops at the first scope where the name is found, so a local variable always shadows a global one with the same name.
Mid Why does creating a list of lambdas in a loop often produce unexpected results?
A closure captures the enclosing variable itself, not its value at the moment the closure was created — so all the lambdas share the same loop variable, and by the time any of them is called, the loop has already finished and the variable holds its final value. [lambda: i for i in range(3)] produces 3 functions that all return 2, not 0/1/2. The standard fix is capturing the current value as a default argument: lambda i=i: i, since default argument values are evaluated once, immediately, at function-definition time.
Senior Why does Python require the global keyword to reassign a global variable inside a function, but not to read one?
Python decides a variable's scope statically, by scanning the function body at compile time — if a name is assigned anywhere in a function, Python treats it as local for the entire function, full stop. Without global, counter += 1 is treated as assigning a local counter, which requires reading it first — but there's no local counter yet, hence UnboundLocalError, not a fallback to the global value. Reading a name that's never assigned in the function has no such ambiguity, so it can fall through Local → Enclosing → Global → Built-in freely. global (or nonlocal for enclosing scopes) explicitly tells Python "assignments to this name in this function should target the outer variable, not create a local one."

Gotchas

A function with no return statement returns None Forgetting return is a common source of silent bugs — the function runs fine, produces no error, and every caller just gets None back instead of the expected value.
Mutable default arguments — the other big trap Covered in depth on Variables & the Memory Model: a mutable default value (like [] or {}) is created once at function-definition time and shared across every call that doesn't override it.
