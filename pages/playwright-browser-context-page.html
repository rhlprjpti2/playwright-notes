Playwright Fundamentals: Browser, Context & Page

Two ways to start a Playwright test: the explicit 3-step hierarchy (full control), or the page fixture shortcut (covers ~90% of real cases). Knowing when the shortcut stops working is the actual interview-worthy part.

Concept

The pytest-playwright plugin ships a global playwright fixture — no need to define or implement it yourself, just reference it as a test argument and start using it. From there, three explicit steps build up to something you can actually automate on: browser → context → page.

The page fixture shortcut

Instead of manually wiring up all three steps every test, the plugin also provides a page fixture (defined inside the Page class of the playwright.sync_api package) that handles browser + context + page internally. Import it explicitly to get IDE autocomplete and make the source traceable:

from playwright.sync_api import Page

def test_playwright_shortcut(page: Page):
    page.goto("https://rahulshettyacademy.com")

The import isn't required for the fixture to work — it's global either way — but without it, the IDE has no idea what type page is, so you lose autocomplete on its methods.

Switching browsers

The page-manipulation code itself doesn't change between browsers — only the launch step does. Swapping Chromium for Firefox is a one-line change:

from playwright.sync_api import Playwright

def test_firefox_browser(playwright: Playwright):
    firefox_browser = playwright.firefox.launch(headless=False)
    page = firefox_browser.new_page()
    page.goto("https://rahulshettyacademy.com")

For a single page, the context step can be skipped — browser.new_page() works directly and uses a single default context.

Interview Q&A

What's the difference between the `playwright` fixture and the `page` fixture in pytest-playwright?
playwright is the low-level global fixture you use to manually launch a specific browser engine, open a context, and open a page — full control over engine choice, headless/headed mode, and number of contexts. page is a higher-level convenience fixture that does all three steps internally, but with fixed assumptions: Chromium engine, headless by default, single context.
Why open a new browser context instead of just using one for everything?
A context is isolated like an incognito window — its own cookies, cache, and session data. If you need to simulate multiple independent users logging in within the same test (or want a guaranteed-fresh session), you open separate contexts rather than risk one login's cookies leaking into a supposedly-fresh flow.
When would you NOT use the page fixture shortcut?
When you need a non-Chromium engine (Firefox/WebKit), when you need headed mode without relying on an external CLI flag, when a test needs multiple browser contexts at once (e.g. a multi-user or OTP-across-sessions flow), or when mixing UI and API testing in one script that requires switching contexts.
How do you run a test in headed mode if you're using the page fixture shortcut?
Pass --headed as an additional argument in the run configuration or CLI command (e.g. pytest --headed), since the fixture's internal launch call isn't directly editable the way it is in the manual 3-step approach.
Why does testing against Playwright's Chromium engine effectively cover both Chrome and Edge?
Both Google Chrome and Microsoft Edge are built on the Chromium engine under the hood, so automating against Playwright's Chromium build simulates real-world behavior for both browsers.

Gotchas

Watch out The page fixture's default is headless and Chromium-only — if a test needs headed mode, you can't just pass a kwarg like the manual approach; it has to come from the run configuration/CLI as --headed.
Import for autocomplete Explicitly importing Page / Playwright from playwright.sync_api isn't required for the fixtures to function — they're globally available regardless — but it's what makes the IDE show autocomplete/IntelliSense on their methods, and it documents where the fixture actually comes from.
