DML Deep Dive

Concept

DML changes row data, not schema structure — that's DDL's job. SELECT is technically part of DML too (it's the read operation), but it gets its own full treatment in Fundamentals; this page is specifically the write side: INSERT, UPDATE, DELETE. Unlike DDL, DML statements participate in transactions normally — they can be rolled back, right up until COMMIT.

INSERT

INSERT INTO employees (first_name, last_name, department)
VALUES ('Ada', 'Lovelace', 'Engineering');

-- Multi-row insert — one round trip instead of N
INSERT INTO employees (first_name, last_name, department) VALUES
  ('Grace', 'Hopper', 'Engineering'),
  ('Katherine', 'Johnson', 'Engineering');

-- INSERT...SELECT — copy rows from one table into another, no app code involved
INSERT INTO engineering_archive (first_name, last_name)
SELECT first_name, last_name FROM employees WHERE department = 'Engineering';
Column order matters when the column list is omitted INSERT INTO employees VALUES ('Ada', 'Lovelace', 'Engineering') (no explicit column list) relies entirely on matching the table's physical column order — a column added or reordered later silently breaks it, or worse, silently inserts values into the wrong columns without any error at all. Always specify the column list explicitly.

UPDATE — and the WHERE clause disaster

UPDATE without a WHERE clause doesn't fail, doesn't warn, and doesn't ask for confirmation — it updates every row in the table. This is the most consequential typo in this entire track, and a legitimate "tell me about a production incident" interview story for a reason.

-- UPDATE with a JOIN — syntax differs by database
-- PostgreSQL / SQL Server style:
UPDATE orders
SET status = 'archived'
FROM customers
WHERE orders.customer_id = customers.id AND customers.active = false;

-- MySQL style:
UPDATE orders
JOIN customers ON orders.customer_id = customers.id
SET orders.status = 'archived'
WHERE customers.active = false;
A teammate runs UPDATE users SET is_active = false; intending to deactivate one specific user. What actually happens?
The habit that actually prevents this Write and run the SELECT with the same WHERE clause first — SELECT * FROM employees WHERE id = 5 — confirm it returns exactly the intended row(s), and only then change SELECT * to UPDATE ... SET ... keeping the identical WHERE. Many database tools and DBA cultures treat this as mandatory for anything touching production data.

Upsert / MERGE

"Insert this row, unless it already exists — then update it instead." A common enough pattern that every major database has a dedicated syntax for it, though the exact keyword differs:

-- PostgreSQL / SQLite
INSERT INTO settings (user_id, theme) VALUES (42, 'dark')
ON CONFLICT (user_id) DO UPDATE SET theme = EXCLUDED.theme;

-- MySQL
INSERT INTO settings (user_id, theme) VALUES (42, 'dark')
ON DUPLICATE KEY UPDATE theme = VALUES(theme);

-- SQL Server / standard SQL
MERGE INTO settings AS target
USING (SELECT 42 AS user_id, 'dark' AS theme) AS source
ON target.user_id = source.user_id
WHEN MATCHED THEN UPDATE SET theme = source.theme
WHEN NOT MATCHED THEN INSERT (user_id, theme) VALUES (source.user_id, source.theme);

All three require a unique constraint or primary key on the conflict column — that's what the database uses to decide whether a row "already exists."

Bulk operations

A thousand single-row INSERT statements, each its own round trip, is dramatically slower than one multi-row INSERT or a database-native bulk-load command (COPY in PostgreSQL, LOAD DATA INFILE in MySQL). For test data seeding specifically, this is the difference between a setup step that takes milliseconds and one that takes minutes — worth knowing as more than trivia if the role touches test infrastructure at all.

Interview Q&A

Junior What happens if you run UPDATE or DELETE without a WHERE clause?
It applies to every row in the table — there's no confirmation, no error, no partial safeguard. UPDATE without WHERE overwrites every row's specified columns; DELETE without WHERE removes every row (though the table itself still exists, unlike TRUNCATE or DROP).
Junior What's the difference between DELETE, TRUNCATE, and DROP?
DELETE (DML) removes rows matching a WHERE clause, can be rolled back, and fires triggers. TRUNCATE (DDL) removes all rows at once by deallocating pages rather than deleting row by row — faster, but no WHERE clause, no rollback in most engines, and no triggers. DROP (DDL) removes the entire table, including its structure — there's no table left to insert into afterward.
Mid Why is it risky to run INSERT INTO table VALUES (...) without listing column names?
It relies on the table's current physical column order matching the value order exactly. A later schema change — a new column added, an existing one reordered — silently breaks this: values can land in the wrong columns with no error raised, rather than failing loudly. Explicitly listing columns makes the statement immune to that class of schema drift.
Mid What's an upsert, and why do INSERT and UPDATE alone not solve the same problem?
An upsert inserts a row if it doesn't exist yet, or updates it if it does — in one atomic statement. Doing this manually (SELECT to check existence, then INSERT or UPDATE based on the result) has a race condition: another connection could insert the same row between the SELECT and the write, causing a duplicate-key error or a lost update. ON CONFLICT / ON DUPLICATE KEY UPDATE / MERGE handle this atomically at the database level instead.
Senior A test suite deletes rows between tests using DELETE FROM table (no WHERE) for cleanup. What's a better approach, and why?
Wrapping each test in a transaction and rolling back at the end, rather than deleting rows outright, is usually better — it's faster (no actual row-by-row deletion), automatically restores exactly the pre-test state, and avoids DELETE's dependency on foreign-key ordering across tables. TRUNCATE is a middle ground when a full rollback-per-test pattern isn't feasible, but it still can't run inside a rolled-back transaction in most engines and will reset auto-increment counters, which can itself break tests that hardcode expected IDs.

Gotchas

Missing WHERE is the single most expensive typo in SQL No error, no confirmation — always run the equivalent SELECT with the same WHERE clause first to verify the target rows before switching it to UPDATE or DELETE.
Implicit column order in INSERT Always list columns explicitly — an omitted column list breaks silently, not loudly, when the schema changes later.
TRUNCATE looks like DELETE but behaves like DDL No WHERE, no rollback in most engines, no row-level triggers, resets auto-increment. Treat it as a structural operation, not a targeted data change.
