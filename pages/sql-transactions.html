Transactions & Concurrency

ACID isn't four abstract words — each letter maps onto a specific bug that happens without it. Isolation levels are a menu of trade-offs between correctness and speed. And a deadlock isn't a bug in one transaction — it's two transactions each waiting on the other, forever, unless the database steps in.

Concept

A transaction groups multiple statements into one all-or-nothing unit — BEGIN, some statements, then COMMIT (make it permanent) or ROLLBACK (undo all of it). Concurrency is what happens when more than one transaction touches the same data at the same time — which is where almost every interesting, interview-relevant problem on this page comes from.

ACID, with a concrete example each

PropertyWhat breaks without it
AtomicityA bank transfer debits one account and credits another as two statements. Without atomicity, a crash between them leaves money debited from one account and never credited to the other — it simply vanishes.
ConsistencyA CHECK constraint says balance can never go negative. Consistency guarantees a transaction that would violate that constraint is rejected entirely, not partially applied.
IsolationTwo transactions run "at the same time" but each behaves (to some configurable degree) as if it were running alone — see isolation levels below for exactly how much.
DurabilityOnce COMMIT returns successfully, the change survives — even a server crash one millisecond later can't undo it. Without durability, a "successful" write could still be silently lost.

Isolation levels and the phenomena they prevent

Four standard levels, each allowing fewer of three specific concurrency phenomena — stricter isolation costs more performance (more locking, more blocking) in exchange for fewer surprises:

LevelDirty readNon-repeatable readPhantom read
Read UncommittedPossiblePossiblePossible
Read Committed (most databases' default)PreventedPossiblePossible
Repeatable ReadPreventedPreventedPossible (varies by engine)
SerializablePreventedPreventedPrevented

The three phenomena, defined precisely:

  • Dirty read — reading another transaction's uncommitted change, which might still be rolled back.
  • Non-repeatable read — reading the same row twice in one transaction and getting two different values, because another transaction committed a change to it in between.
  • Phantom read — re-running the same query twice in one transaction and getting a different set of rows, because another transaction inserted or deleted rows matching the query's condition in between.

Why READ UNCOMMITTED is rarely used in practice A dirty read means a decision (a report figure, a business-logic branch) can be based on data that's about to be rolled back and effectively never existed. Most applications default to READ COMMITTED or stricter for exactly this reason — READ UNCOMMITTED trades correctness for a small amount of extra concurrency, and it's rarely a trade worth making.

Shared vs. exclusive locks

Lock typeAllows
Shared (read) lockMultiple transactions can hold a shared lock on the same row at once — many concurrent readers, no conflict.
Exclusive (write) lockOnly one transaction can hold it, and no other transaction can hold any lock (shared or exclusive) on that row at the same time — writers block everyone else.

This is the underlying mechanism isolation levels are built from — a stricter isolation level generally means holding locks for longer, or acquiring more of them, which is the actual source of the performance cost mentioned above.

Interview Q&A

Junior What does ACID stand for?
Atomicity (all-or-nothing execution), Consistency (a transaction can't leave the database violating its constraints), Isolation (concurrent transactions don't see each other's uncommitted changes, to a configurable degree), and Durability (a committed change survives a crash).
Mid What's the difference between a dirty read and a non-repeatable read?
A dirty read is seeing another transaction's uncommitted change — data that might be rolled back and never actually exist. A non-repeatable read is reading the same row twice within one transaction and getting two different values because another transaction committed a change in between — the data was real and committed both times, it just changed.
Mid What causes a deadlock, and how does the database resolve it?
Two (or more) transactions each hold a lock the other one needs, forming a cycle where neither can proceed. The database's deadlock detector identifies the cycle and forcibly rolls back one transaction (chosen by internal cost heuristics) to break it, letting the other continue. The rolled-back transaction's application code is expected to catch this and retry.
Senior Why might a team choose Read Committed over Serializable even though Serializable is strictly safer?
Stricter isolation means more locking and more blocking between concurrent transactions, which directly costs throughput and can increase deadlock frequency. Read Committed is a deliberate trade — accepting the possibility of non-repeatable and phantom reads in exchange for significantly better concurrency — and it's the right choice for most application code, which either doesn't rely on those guarantees or handles them another way (e.g., optimistic locking with a version column).

Gotchas

READ UNCOMMITTED in production is a red flag The performance gain rarely justifies the correctness risk — dirty reads mean decisions get made on data that may never have actually existed.
A "successful" write can still deadlock later in the same transaction The deadlock isn't detected at the first UPDATE — it's detected only once the cycle actually forms. Code shouldn't assume a transaction that started fine will finish fine.
Inconsistent lock ordering across an application is the most common deadlock root cause If different code paths update the same two tables in a different order, a deadlock is a matter of when, not if, under real concurrent load.
