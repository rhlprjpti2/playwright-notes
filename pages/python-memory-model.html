Variables & the Memory Model

A Python variable is not a box that holds a value. It's a name tag pointing at an object living somewhere else — in the heap. That single correction explains aliasing, the mutable-default-argument trap, and why is and == disagree, all at once.

Names, not boxes

In a language like C, a variable is a labeled slot of memory — assigning to it overwrites what's in that slot. Python works differently: every value is an object living in the heap, and a variable is just a name bound to one of those objects. Assignment doesn't copy a value into a slot; it points a name at an object.

Two consequences fall directly out of that one fact:

  • Multiple names can point at the same object. b = a doesn't copy a's value — it makes b point at the exact same object a already points at.
  • "Changing a variable" can mean two very different things — pointing the name at a different object (rebinding), or changing the object itself while every name still pointing at it sees the change (mutating). Which one happens depends entirely on whether the object is mutable.

Watch it happen

Step through five lines of code and watch what's actually happening: names moving between objects in the heap, not values changing in boxes.

The one-sentence rule Rebinding (b = 5) moves a name to a different object and never affects other names. Mutating (lst2.append(4)) changes the object itself, so every name pointing at it sees the change. Whether an operation rebinds or mutates depends on the type — not on which variable you used.

Mutable vs immutable

This single property — can the object change in place, or not — determines whether aliasing is a non-issue or a bug waiting to happen. It's a fixed property of the type, not something you choose per variable.

Notice tuple is immutable but can contain mutable objects — t = ([1,2], 3). The tuple itself can never point at different objects, but if one of those objects is a list, that list can still be mutated in place. "Immutable" describes the container's bindings, not everything reachable through it.

is vs ==

Once "variable = name pointing at an object" clicks, this distinction stops being a rule to memorize:

AsksUse it for
==Do these two objects have equal values?Almost everything — comparing data
isAre these two names pointing at the exact same object in memory?is None, is True/is False, and identity checks specifically
 
a = [1, 2, 3]
b = [1, 2, 3]
a == b   # True  — same values
a is b   # False — two different list objects that happen to hold equal values

c = a
c is a   # True  — c and a point at the literal same object
Why is None, not == None None is a singleton — there is exactly one None object for the entire life of your program, so identity comparison is both correct and slightly faster than equality. It's also safer: a custom class could override __eq__ in a way that makes obj == None behave unexpectedly, but no class can hijack is.

The mutable-default trap

This is one of the most-cited Python gotchas — and it's a direct consequence of everything above. A function's default argument value is created once, when the def statement runs, not fresh on every call:

def add_item(item, cart=[]):    # this list is created ONCE, at def time
    cart.append(item)
    return cart

add_item("apple")     # ['apple']
add_item("banana")    # ['apple', 'banana']  -- not a fresh cart!

Every call that doesn't pass cart explicitly reuses the exact same list object — because a default value is just another name bound to an object, and that binding happens once. The fix is a well-known idiom:

def add_item(item, cart=None):
    if cart is None:
        cart = []          # a fresh list object, created fresh every call
    cart.append(item)
    return cart

Interview Q&A

Junior What's the difference between is and ==?
== compares values — are these two objects equal? is compares identity — are these two names pointing at the literal same object in memory. Two separate lists with identical contents are == but not is. Use is specifically for None/True/False and genuine identity checks; use == for everything else.
Mid Explain what happens in memory when you write b = a for a list, versus for an int.
In both cases, no new object is created — b is simply pointed at the same object a already points at. The difference shows up later: if the object is a mutable list and you call b.append(x), the object itself changes, so a sees it too, because both names point at the same object. If the object is an immutable int and you write b = b + 1, that creates a brand-new int object and rebinds only b — a is untouched.
Scenario A function that appends to a "default empty list" parameter accumulates results across unrelated calls. What's wrong and how do you fix it?
The classic mutable-default-argument bug — def f(x, acc=[]) creates that list once, when the function is defined, not per call. Every call that omits acc shares and mutates the same list object. Fix: default to None, and create a fresh list inside the function body if it's still None — if acc is None: acc = [] — so a new object is created on every call instead of once at definition time.
Senior Is Python "pass by value" or "pass by reference"?
Neither term fits cleanly — Python is "pass by object reference" (also called "pass by assignment"). The function parameter becomes a new name pointing at the same object the caller's argument pointed at — not a copy of a value (as in true pass-by-value), and not an alias that lets you rebind the caller's variable (as in true pass-by-reference, e.g. C++'s &). Concretely: mutating a passed-in mutable object (e.g. lst.append(x)) is visible to the caller; rebinding the parameter name itself (lst = []) inside the function is not — the caller's variable still points at the original object.
Mid Is a tuple truly immutable if it contains a list?
The tuple's own bindings are immutable — it can never be made to point at different objects in its slots. But if one of those slots holds a mutable object like a list, that list can still be mutated in place through the tuple: t = ([1,2], 3); t[0].append(4) works fine. "Immutable" describes what the container itself can be reassigned to, not everything transitively reachable through it.

Gotchas

Small-integer caching CPython caches (interns) small integers from -5 to 256 and reuses the same object for them. So a = 100; b = 100; a is b is True — not because of aliasing you wrote, but as a CPython implementation detail. Try the same with 1000 and it's usually False. Never rely on is for integer comparison — this is exactly why == is the correct default and is is reserved for identity-specific cases like None.
String interning is similarly unreliable to depend on Short, simple string literals are sometimes interned (reused) by CPython too, making is appear to work for string comparison in quick tests. This is an optimization detail, not a language guarantee — it can differ between Python versions and even between how a string was constructed. Use == for string comparison, always.
