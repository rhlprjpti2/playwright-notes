Joins & Relationships

The single most-tested SQL topic in any interview loop. Not the Venn-diagram version — actual row matching, because the Venn-diagram explanation quietly falls apart the moment duplicate keys enter the picture, which is exactly where interview follow-up questions go.

Concept

A join combines rows from two (or more) tables based on a related column — almost always a foreign key pointing at another table's primary key. Every join type answers the same underlying question differently: what happens to a row on one side that has no match on the other side? That single question is what actually separates INNER from LEFT from FULL OUTER — everything else about them is identical.

INNER JOIN vs LEFT JOIN

The pairing that comes up in almost every SQL interview, using two small tables: customers (Ada, Grace, Katherine) and orders (one order each for Ada and Katherine — Grace has never ordered anything).

Using a LEFT JOIN from customers to orders, how would you find every customer who has never placed an order?

RIGHT, FULL OUTER, CROSS

Join typeKeeps
RIGHT JOINEvery row from the right table, NULL-filling unmatched left columns — the mirror image of LEFT JOIN. Rare in practice; most people rewrite it as a LEFT JOIN with the tables swapped, since it reads more naturally left to right.
FULL OUTER JOINEvery row from both tables — matched rows combined, unmatched rows from either side NULL-filled on the other side. Not supported directly in MySQL (emulated with a LEFT JOIN UNION RIGHT JOIN).
CROSS JOINEvery row from the first table paired with every row from the second — no ON condition at all. N rows × M rows. Rarely intentional; usually the accidental result of a missing join condition.
An accidental CROSS JOIN is a classic production incident Forgetting the ON/WHERE condition entirely (or joining on the wrong columns, such that every row matches every row) silently produces a cartesian product — a query expected to return a few thousand rows can return billions and lock up the database.

SELF JOIN

Not a distinct join type — an ordinary join where a table is joined to itself, using two aliases to tell the two "copies" apart. The classic example: an employees table where manager_id points back at another row's id in the same table.

SELECT e.first_name AS employee, m.first_name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;

The LEFT JOIN here matters for the same reason as above — an employee with no manager (manager_id IS NULL, e.g. the CEO) would be silently dropped by an INNER JOIN, since NULL never matches anything in an ON condition either.

The WHERE-clause trap on outer joins

A filter placed in WHERE instead of the join's ON clause quietly turns a LEFT JOIN back into an INNER JOIN — one of the most common real bugs involving joins, and a favorite "spot the mistake" interview question.

-- Looks like "all customers, with their shipped orders if any" — it is NOT
SELECT * FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE o.status = 'shipped';          -- BUG: silently drops every customer with no orders

-- Correct — the filter belongs in the join condition, not WHERE
SELECT * FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id AND o.status = 'shipped';

Recall the logical execution order from Fundamentals: WHERE runs after the join has already produced its result set, including the NULL-filled rows for unmatched customers. o.status = 'shipped' can never be true when o.status is NULL (three-valued logic again), so every one of those NULL-filled rows gets filtered out — silently converting the LEFT JOIN's whole point into an INNER JOIN.

Interview Q&A

Junior What's the difference between INNER JOIN and LEFT JOIN?
INNER JOIN keeps only rows that have a match on both sides — a row with no match is dropped entirely. LEFT JOIN keeps every row from the left table regardless of whether it has a match, filling the right side's columns with NULL when there's no match.
Mid How do you find all customers who have never placed an order?
LEFT JOIN customers to orders, then filter WHERE orders.some_column IS NULL. Customers with no matching order have every order column as NULL after the join, so filtering for NULL isolates exactly the unmatched customers.
Mid A LEFT JOIN with a WHERE clause on the right table's column is returning fewer rows than expected. Why?
If the WHERE condition filters on a right-table column (e.g. WHERE orders.status = 'shipped'), it also filters out every row where that column is NULL — which includes all the unmatched left-side rows the LEFT JOIN was specifically trying to preserve. This silently turns the LEFT JOIN into the equivalent of an INNER JOIN. The fix is moving that condition into the join's ON clause instead of WHERE.
Mid What is a self join, and why does the query need table aliases?
A self join joins a table to itself — typically to relate rows within the same table, like an employee to their manager who is also a row in the employees table. Aliases (e.g. e and m) are required because the query references the same table twice and SQL needs a way to disambiguate which "copy" a given column reference belongs to.
Senior What causes an accidental CROSS JOIN, and why is it dangerous?
Missing or incorrect join conditions — an ON clause that's omitted, or one where every row happens to match every row — produce a cartesian product: every row from one table paired with every row from the other, N × M results. On tables of any real size this can produce an enormous, database-locking result set from what looked like an ordinary query, making it a genuine production-incident cause rather than just a theoretical concern.

Gotchas

WHERE on the outer side of a LEFT/RIGHT JOIN Silently degrades it to an INNER JOIN. Filters specific to the "nullable" side belong in the ON clause.
Missing join condition = accidental CROSS JOIN Always double check the ON clause exists and references the actual relationship — not just columns that happen to compile.
NULL never matches in an ON clause, including against itself A self join on a nullable foreign key (like manager_id) needs LEFT JOIN, not INNER JOIN, or every row with a NULL in that column disappears from the result.
