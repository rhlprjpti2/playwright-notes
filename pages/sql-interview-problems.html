The Nth highest salary

The same tie-handling mechanic from Window Functions — DENSE_RANK() is specifically the right tool here because "2nd highest salary" should mean 2nd highest distinct value, not 2nd row:

SELECT DISTINCT salary
FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) ranked
WHERE rnk = 2;

Why not ROW_NUMBER() or plain LIMIT/OFFSET here ROW_NUMBER() would give Ada 1 and Grace 2 — making "2nd highest" resolve to 90 again, the exact same salary as 1st, which isn't the intent. LIMIT 1 OFFSET 1 on ORDER BY salary DESC has the identical problem — it returns the 2nd row, not the 2nd distinct value. DENSE_RANK is specifically the tie-aware tool for "Nth distinct value" questions.

Find duplicate rows

Group by whatever defines "duplicate" for the data, then keep only groups where more than one row shares those values:

SELECT email, COUNT(*) AS occurrences
FROM users
GROUP BY email
HAVING COUNT(*) > 1;

This is a direct application of HAVING — filtering on COUNT(*), which only exists after grouping, so it has to be HAVING, not WHERE. To then actually delete the duplicates, keeping just one copy of each:

DELETE FROM users
WHERE id NOT IN (
  SELECT MIN(id) FROM users GROUP BY email   -- keep the lowest id per email
);

Running total

A window function with no PARTITION BY at all treats the whole result as one partition — and the frame clause makes each row sum everything up to and including itself:

SELECT order_date, amount,
       SUM(amount) OVER (ORDER BY order_date) AS running_total
FROM orders;

SUM() OVER (ORDER BY order_date) — with no explicit frame clause — defaults to "every row from the start up through the current one," which is exactly the running-total behavior. This is the same OVER (...) mechanism from Window Functions, just with SUM instead of a ranking function.

Consecutive-day streaks

Find each user's longest run of consecutive login days — a genuinely clever trick, not just another aggregate. Subtracting a row number from a date produces the same result for every date in an unbroken run, and a different result the moment there's a gap:

SELECT user_id, login_date,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) AS rn,
       login_date - ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) AS island
FROM logins;

The first three rows (Jan 1–3, genuinely consecutive) all compute the identical "island" value of Dec 31 — each date increases by 1 and so does the row number, so the difference stays constant. The moment there's a gap (no Jan 4), the row number keeps incrementing by 1 but the date jumped by 2, so the difference shifts to a new value. Grouping by that computed "island" column and counting rows per group directly gives the length of each consecutive streak — GROUP BY user_id, island, then the largest COUNT(*) per user is their longest streak.

Why does subtracting ROW_NUMBER() from the date produce the same value for every date in a consecutive run?

Interview Q&A

Mid Write a query for the 2nd highest salary, handling ties correctly.
Wrap DENSE_RANK() OVER (ORDER BY salary DESC) in a subquery or CTE, then filter the outer query WHERE rnk = 2. DENSE_RANK is specifically correct here (over ROW_NUMBER or LIMIT/OFFSET) because it ranks by distinct value — two people tied for 1st both get rank 1, and the next distinct salary correctly gets rank 2.
Mid How would you find and remove duplicate rows, keeping exactly one copy of each?
GROUP BY the columns that define a duplicate, HAVING COUNT(*) > 1 to find them. To delete: DELETE WHERE id NOT IN (SELECT MIN(id) FROM table GROUP BY those same columns) — keeping the row with the lowest id (or any other deterministic tiebreaker) per group and removing the rest.
Senior Explain the "gaps and islands" technique for finding consecutive-date runs.
Compute ROW_NUMBER() OVER (PARTITION BY the grouping column ORDER BY date), then subtract it from the date itself. For any unbroken run of consecutive dates, both the date and the row number increase by exactly 1 per row, so their difference is constant across the whole run — a stable "island" identifier. The moment there's a gap, the row number keeps incrementing by 1 but the date jumps by more, shifting the difference to a new value and starting a new island. Grouping by that computed difference and counting rows per group gives the length of each consecutive streak directly.

Gotchas

ROW_NUMBER() for "Nth highest" silently ignores ties Defaults to treating tied values as distinct ranks — almost never the actual intent behind "2nd highest X."
Deleting duplicates without a deterministic tiebreaker "Keep the lowest id" is deterministic and repeatable; "keep whichever row the database happens to return first" is not, and can behave differently across runs or database versions.
A running total without ORDER BY inside OVER() is undefined Same rule as everywhere else on this track — window functions that depend on row order need an explicit ORDER BY inside OVER(...), or the accumulation order isn't guaranteed.
