Playwright Core Locators

get_by_label, get_by_role, CSS locators, get_by_text — which one to reach for depends entirely on what the DOM actually exposes, not personal preference. The label-locator failure conditions are a genuine interview trap.

Concept

Playwright gives you several complementary ways to locate an element, ranked roughly by how "semantic" the underlying attribute is: a form field's associated label, a component's accessibility role, a raw CSS selector as a universal fallback, or the visible text an element contains.

Choosing a strategy

get_by_label

page.get_by_label("Username").fill("RahulAcademy")
page.get_by_label("Password").fill("learning")

This only works if one of two DOM conditions is true:

  • The <input> is nested inside the <label> tag, or
  • The <label for="id"> attribute exactly matches the input's own id attribute.
Real failure case from this lecture On a second practice page, the label's for attribute was "email" but the input's actual id was "userEmail" — a mismatch. Since the input also wasn't nested inside the label, get_by_label failed to find it despite a label being visibly present on the page.
HTML: <label for="email">Email</label> <input id="userEmail"> (input not nested inside the label). Does page.get_by_label("Email") find this input?

get_by_role

page.get_by_role("combobox").select_option("teach")
page.get_by_role("button", name="Sign In").click()
page.get_by_role("link", name="Terms and Conditions").click()

Identifies an element by its accessibility/semantic role — combobox, button, link, checkbox, alert, image, and more. When multiple elements share the same role (e.g. several buttons on a page), the optional name= parameter filters down to the one whose visible name matches — role and filter are bundled into the single call.

For dropdowns, .select_option() selects by the underlying HTML <option value="..."> attribute — which is not necessarily the same string as what's visually displayed to the user.

Beyond this video — common ARIA roles, not just the 3 named in the course The video names combobox, button, link, checkbox, alert, and image. The full role vocabulary is much larger — the ones you'll actually hit most often in real apps: textbox, radio, heading, list / listitem, tab / tabpanel, dialog, table / row / cell, navigation, banner, search, menu / menuitem, and progressbar. Any element with an implicit or explicit ARIA role can be targeted this way — worth knowing since interviewers sometimes ask "how would you locate X" for elements that aren't literally form controls.

CSS locators

The universal fallback — works on anything, including custom components with no ARIA role (e.g. plain <div> cards). Derived directly from DOM attributes via page.locator(css_selector):

DOM attributeCSS selector syntaxExample
id="terms"#id#terms
class="text-info".class-name.text-info
tag namebare tag namerarely unique — not much preferred

For a checkbox specifically, Playwright provides a semantic .check() action (in addition to the generic .click()) that specifically validates and checks a checkbox element:

page.locator("#terms").check()

To grab an element purely by its visible text (e.g. an alert/message block, without knowing its CSS class):

page.get_by_text("Incorrect username or password")

The full get_by_* family

The video covers get_by_label, get_by_role, and get_by_text — the three you'll use most. Playwright's locator API has a few more siblings worth knowing so you're not caught off guard if an interviewer asks about a case these three don't cleanly cover:

Beyond this video — not mentioned in the course, but standard Playwright API
  • get_by_placeholder("Enter email") — matches an input by its placeholder text, useful when there's no associated label at all.
  • get_by_alt_text("Company logo") — matches an <img> by its alt attribute.
  • get_by_title("Close dialog") — matches an element by its title attribute (the tooltip text).
  • get_by_test_id("submit-btn") — matches a custom test-id attribute (data-testid by default). The most resilient option when a team deliberately adds test hooks, since it doesn't depend on visible text, styling, or DOM structure at all.

Preference order most teams converge on, roughly: get_by_role (closest to how a real user/assistive tech perceives the page) → get_by_label / get_by_placeholder for form fields → get_by_test_id when the team maintains them → CSS as the last resort.

Interview Q&A

What two DOM conditions must hold for get_by_label to successfully find an element?
Either the input element is nested inside the <label> tag itself, or the label's for attribute exactly matches the input's id attribute. If neither holds, get_by_label won't find it — even if a label is visually present on the page.
How do you disambiguate multiple elements that share the same role, like several buttons on a page?
Pass the name= parameter to get_by_role, e.g. get_by_role("button", name="Sign In") — Playwright gets all elements with that role first, then filters to the one whose visible/accessible name matches.
When would you fall back to a CSS locator instead of get_by_role or get_by_label?
When the element is a custom component with no semantic ARIA role attached — e.g. a plain <div>-based product card — or a form field with no associated label. CSS built from id/class attributes works regardless of role or label semantics.
What's the difference between what select_option chooses and what's visually shown in a dropdown?
select_option targets the underlying HTML option value attribute, which is not necessarily identical to the text visually displayed to the user in the dropdown UI.

Gotchas

Watch out A visually-present label doesn't guarantee get_by_label will work — always check whether the input is actually nested in the label or correctly linked via for/id before assuming this locator is usable.
Watch out Bare tag-name CSS selectors are rarely unique on a real page (multiple labels, multiple divs, etc.) — prefer id or class-based selectors unless you're deliberately grabbing every match.
