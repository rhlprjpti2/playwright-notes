SQL for Test Automation

The part of this track that's actually SDET-specific rather than generic SQL knowledge: querying the database directly to assert on real application state, seeding and cleaning up test data without pollution between tests, and verifying a data migration actually moved everything correctly.

Concept

A UI test that clicks "Save" and then only checks for a success toast is trusting the application's own claim that the save worked. Querying the database directly afterward — the same reasoning as the DML page's "prove persistence, not just a response" point for API tests — is the difference between testing that something looked successful and testing that it actually happened.

Running SQL from Python

import psycopg2

conn = psycopg2.connect(host="localhost", dbname="test_db", user="test_user")
cur = conn.cursor()
cur.execute("SELECT status FROM orders WHERE id = %s", (order_id,))
row = cur.fetchone()
assert row[0] == "shipped"
conn.close()

# SQLAlchemy — a higher-level, more Pythonic layer over the same idea
from sqlalchemy import create_engine, text
engine = create_engine("postgresql://test_user@localhost/test_db")
with engine.connect() as conn:
    result = conn.execute(text("SELECT status FROM orders WHERE id = :id"), {"id": order_id})
    assert result.scalar() == "shipped"
Always parameterize — never format a value into the SQL string f"SELECT * FROM orders WHERE id = {order_id}" is a SQL injection vector even in test code, and it breaks outright on any value containing a quote. The %s / :id placeholders above hand the value to the driver separately from the query text — the same reasoning Playwright's own parameterized locators follow for a different kind of injection risk.

This is the same principle as the API Testing page's create-then-verify pattern, applied one layer deeper — instead of calling the API back to confirm, the test reads the actual row the API call was supposed to produce.

Seeding and cleaning up test data

A dedicated seed_test_account(...) stored procedure or a Python factory function — either works, but the goal is the same: one reusable, named way to create valid test data, instead of every test hand-rolling its own INSERT statements that quietly drift out of sync with the schema over time.

@pytest.fixture
def test_customer(db_connection):
    cur = db_connection.cursor()
    cur.execute(
        "INSERT INTO customers (name, email) VALUES (%s, %s) RETURNING id",
        ("Test Customer", f"test-{uuid.uuid4()}@example.com")
    )
    customer_id = cur.fetchone()[0]
    yield customer_id

The yield-based setup/teardown shape here is the exact same mechanism covered in Pytest Fixtures — a database fixture is not a different concept, just a fixture whose setup happens to be a SQL INSERT.

ETL / data migration testing

Verifying a migration moved data correctly comes down to comparing source and destination on three levels, each catching a different failure mode:

-- 1. Row counts match — catches dropped or duplicated rows
SELECT COUNT(*) FROM source_db.orders;
SELECT COUNT(*) FROM destination_db.orders;

-- 2. Aggregate checksums match — catches silent value corruption row counts alone would miss
SELECT SUM(amount), COUNT(DISTINCT customer_id) FROM source_db.orders;
SELECT SUM(amount), COUNT(DISTINCT customer_id) FROM destination_db.orders;

-- 3. Spot-check specific rows for exact field-level equality
SELECT * FROM source_db.orders WHERE id = 12345;
SELECT * FROM destination_db.orders WHERE id = 12345;
Row counts matching is necessary, not sufficient Two tables can have identical row counts while every single amount value is silently off by a currency-conversion bug — matching counts alone proves nothing was dropped or duplicated, not that the data itself is correct. All three levels are needed for real confidence.

Interview Q&A

Junior Why query the database directly in a test instead of trusting the UI's success message?
A success message only proves the application claims the action worked — it doesn't prove the underlying data was actually written correctly, or at all. Querying the database directly verifies the real, persisted outcome independent of what the UI happens to display.
Mid Why is transaction-per-test rollback usually preferred over DELETE-based cleanup between tests?
It's faster (no actual row-by-row deletion), it automatically restores the exact pre-test state, and it avoids DELETE's dependency on getting foreign-key deletion order right across multiple tables. The trade-off is that it doesn't work for testing something that itself depends on a real COMMIT (e.g. testing a second database connection's visibility of the data).
Mid How would you verify a data migration between two databases moved everything correctly?
At least three levels: row counts matching (catches dropped/duplicated rows), aggregate checksums like SUM or COUNT DISTINCT matching (catches value corruption that row counts alone would miss), and spot-checking individual rows for exact field-level equality. Row counts alone are not sufficient — they can match while every value is subtly wrong.
Senior A test suite's database fixtures are getting slow as the suite grows. What would you investigate?
Whether cleanup is transaction-rollback-based (fast) or DELETE-based (row-by-row, and often requires walking foreign-key dependency order across many tables — one of the more common actual causes of fixture slowdown at scale). Also worth checking for N+1-style seeding — a fixture that seeds related data by looping and inserting one row per iteration instead of a single multi-row INSERT.

Gotchas

String-formatting a value into test SQL is still SQL injection risk Always parameterize, even in test-only code — test databases get real, sometimes sensitive-shaped data too.
Transaction-rollback isolation can't test cross-connection visibility If a test genuinely needs to verify what a second, separate connection sees, an uncommitted transaction on the first connection is invisible to it by design — that specific scenario needs a real COMMIT and explicit cleanup instead.
Row-count-only migration verification misses corruption Always pair count checks with an aggregate checksum or field-level spot check.
