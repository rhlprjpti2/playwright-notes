API Testing & Assertion Validation

Playwright isn't only a browser driver — APIRequestContext sends real HTTP requests with no browser involved at all. Same library, same expect(), a completely different (and much faster) kind of test. This page covers the whole range: firing a request, asserting the response, and the advanced patterns — auth, hybrid API+UI, and where this stops being "API testing" and becomes route mocking.

Why API testing at all

Every other page on this site drives a browser: launch Chromium, render the page, wait for elements, click, wait again. That's necessary when the thing under test is the UI — but a huge share of what an application does never touches a browser at all. APIRequestContext sends an HTTP request straight to the server and gets a response back, with no rendering, no waiting for elements, no browser process at all.

UI test (page)API test (APIRequestContext)
What it drivesA real rendered browser pageA direct HTTP request/response
SpeedSeconds per test — render, locate, auto-waitMilliseconds — no rendering at all
What it can proveThe user-visible flow actually worksThe backend contract is correct — status, headers, JSON shape
Flakiness sourceTiming, animations, layout shiftsAlmost none — it's just a request

In practice the two aren't competitors — they're used together. A common pattern (covered in Hybrid API + UI testing below) is using the API to set up state fast, then a UI test to verify only the specific flow that actually needs a browser.

Getting a request context

There are three ways to get an APIRequestContext in a Python Playwright test, and the difference between them is whether it shares a session with a browser page:

SourceTied to a browser?When to use it
page.requestYes — same cookies/storage as pageCalling an API using the exact session a UI test already logged into
playwright.request.new_context(...)No — a standalone clientPure API tests with no browser at all — fastest option, most control over headers/base_url
api_request_context fixtureNo — same as aboveShorthand for the standalone context in pytest-playwright; teardown is automatic
 
# Standalone context — created manually, must be disposed
request_context = playwright.request.new_context(
    base_url="https://api.example.com",
    extra_http_headers={"Accept": "application/json"},
)
response = request_context.get("/users/1")
request_context.dispose()   # closes the underlying connection pool

# Same thing via the pytest-playwright fixture — no manual dispose needed
def test_get_user(api_request_context):
    response = api_request_context.get("/users/1")
    assert response.ok
Reach for the fixture by default api_request_context gives you the standalone client with teardown already handled by the plugin. Only build a context manually with playwright.request.new_context() when a single test genuinely needs more than one client — different base URLs, different auth, that kind of thing.

Making requests

An APIRequestContext has one method per HTTP verb, plus a generic .fetch() for anything unusual:

MethodTypical use
.get(url, params=...)Read a resource. params becomes the query string.
.post(url, data=..., json=...)Create a resource. json= auto-serializes and sets Content-Type: application/json — usually what you want over data=.
.put(url, json=...)Replace a resource entirely.
.patch(url, json=...)Partially update a resource.
.delete(url)Remove a resource.
.fetch(url, method="...")Generic escape hatch — any verb, most explicit control over the request.
 
response = api_request_context.get(
    "/search",
    params={"q": "playwright", "limit": 10},
)

response = api_request_context.post(
    "/users",
    json={"name": "Ada Lovelace", "role": "admin"},
)
data= vs json= data={"name": "Ada"} sends a form-encoded body. json={"name": "Ada"} serializes to a JSON string and sets the content-type header for you. Passing a Python dict as data= when the API expects JSON is a common first mistake — the server sees form fields, not a JSON body.

Status assertions

Playwright's expect() works on API responses the same way it works on locators — to_be_ok() is the response-side assertion, and it passes for any status in the 200–299 range, not just exactly 200:

from playwright.sync_api import expect

response = api_request_context.get("/users/1")
expect(response).to_be_ok()          # passes for 200, 201, 204...

# equivalent, without expect()
assert response.ok
assert response.status == 200
assert 200 <= response.status < 300

Validating the response body

to_be_ok() only checks the status — a 200 with the wrong data still passes it. Validating the actual payload is a separate, manual step using response.json():

response = api_request_context.get("/users/1")
expect(response).to_be_ok()          # status is fine...

body = response.json()
assert body["name"] == "Ada Lovelace"   # ...but is the DATA right?
assert body["role"] == "admin"
assert "email" in body                   # shape check — key must exist

The interview trap "The API returned 200, so the test passed" is not the same statement as "the API returned the right data." A backend bug that silently returns the wrong record, a stale cache, an empty list where ten items were expected — all of those are still 200. Status assertions and body assertions are two separate checks, and skipping the second one is the single most common gap in API test suites.

Authenticated requests

Most real APIs require a token. The usual shape: log in once, capture the token, then attach it to every subsequent request via headers on the context itself — rather than passing it into every single call:

login_response = api_request_context.post("/auth/login", json={
    "username": "test_user", "password": "..."
})
token = login_response.json()["access_token"]

authed_context = playwright.request.new_context(
    base_url="https://api.example.com",
    extra_http_headers={"Authorization": f"Bearer {token}"},
)
response = authed_context.get("/me")
expect(response).to_be_ok()

Headers set via extra_http_headers on the context apply to every request made through it — no need to repeat headers={"Authorization": ...} on each call. A context can also be created directly from a saved session with storage_state=, reusing cookies captured from an earlier login instead of hitting the login endpoint every test.

File uploads

Multipart form data — the shape a real file upload endpoint expects — is sent via the multipart parameter:

response = api_request_context.post(
    "/avatar",
    multipart={
        "file": {
            "name": "profile.png",
            "mimeType": "image/png",
            "buffer": open("profile.png", "rb").read(),
        },
        "userId": "4821",   # plain fields can sit alongside the file
    },
)
expect(response).to_be_ok()

Hybrid API + UI testing

The two aren't an either/or choice. The most common production pattern uses the API to get the application into the right state quickly, then a UI test to verify only the part that genuinely needs a rendered browser:

PatternWhy
Seed data via API, verify via UICreating 50 test orders by clicking through the UI 50 times is slow and flaky. POST them via the API in milliseconds, then load the UI once to verify the list renders correctly.
Log in via API, reuse the session in the browserLog in through /auth/login, capture the resulting cookies/token as storage_state, then open a browser context already authenticated — skips re-typing credentials through a login form in every test.
page.request mid-UI-testBecause page.request shares the page's own session, a UI test can call an internal API directly to check a side effect (e.g. "did that click actually persist to the backend?") without a second, separate login.
 
# Log in via API, hand the session to a browser context
login_response = api_request_context.post("/auth/login", json={
    "username": "test_user", "password": "..."
})
storage_state = api_request_context.storage_state()

context = browser.new_context(storage_state=storage_state)
page = context.new_page()
page.goto("/dashboard")   # already logged in — no form to fill

API testing vs. route interception

These get confused because both involve "Playwright" and "HTTP requests," but they answer opposite questions:

API testing (APIRequestContext)Route interception (page.route())
What's being testedThe real backend — a genuine request leaves the machineThe frontend's handling of a response — the real backend is never hit
Where the response comes fromThe actual serverWherever you tell it to — a hand-written fake response
Typical useVerifying a contract, seeding data, checking a side effectForcing an error state, a slow network, or an edge-case payload the real backend won't reliably produce on demand
 
# API testing — a REAL request, testing the real backend
response = api_request_context.get("/orders")
expect(response).to_be_ok()

# Route interception — the browser never reaches the real backend at all
page.route("**/orders", lambda route: route.fulfill(
    status=500, json={"error": "Internal Server Error"}
))
page.goto("/orders")   # UI's error-state handling is what's under test here
Same site, different mechanism If this "register something before it happens" shape feels familiar, it's the same family as dialog handlers and popup capture — page.route() is also registered before the navigation that triggers it, not called reactively afterwards. Route interception gets a full page of its own — fulfill() vs. continue_(), a full request/response reference, and the related trick of skipping login via injected session storage — at Network Interception & Session Storage.

Interview Q&A

Junior What is APIRequestContext and how is it different from using page?
APIRequestContext sends real HTTP requests directly, with no browser involved — no rendering, no waiting for elements, no page at all. page drives an actual browser and is for testing what a user sees and clicks. They can even coexist: page.request is an APIRequestContext that shares the same page's cookies and session.
Junior Does expect(response).to_be_ok() validate the response body?
No — it only checks that response.status is in the 200–299 range. A 200 response with completely wrong or missing data still passes to_be_ok(). Validating the actual payload requires a separate step: parse it with response.json() and assert on the specific fields.
Mid What's the difference between data= and json= on .post()?
json= serializes the given value to a JSON string and sets Content-Type: application/json automatically — the usual choice for a JSON API. data= sends a form-encoded body instead. Passing a dict as data= to an endpoint expecting JSON is a common bug — the server receives form fields, not a JSON object, and often responds with a validation error that looks unrelated to the actual mistake.
Mid Why would you use page.request instead of a standalone api_request_context?
page.request shares the browser context's cookies and storage state — so a call made through it hits the API as the exact same logged-in session the page is using. That's the right tool when a UI test needs to check a backend side effect of something it just did in the browser, without a second, separate authentication flow. A standalone context is the right tool when there's no browser session to share at all — pure API tests.
Mid A test asserts response.status == 201 after a POST. Is that a complete test?
Not on its own. It proves the server accepted the request and responded with the right status code — it doesn't prove the resource was actually persisted. Some backends can echo back a plausible-looking response without saving anything (a bug, a cache, a mock left on by accident). The stronger version follows up with a separate GET on the resource and asserts the data comes back correctly — proving persistence, not just a well-formed response.
Senior When would you choose API testing over route interception, or the other way around?
API testing sends a real request and is for validating the actual backend contract — status codes, response shape, side effects like persistence. Route interception (page.route()) never reaches the real backend at all — it's for controlling what the frontend receives, which matters when testing how the UI reacts to conditions the real backend won't reliably reproduce on demand: a 500 error, a 10-second delay, a malformed payload. Conflating the two is a common mistake — a route-intercepted test proves nothing about whether the real API actually behaves that way.
Senior Why combine API and UI testing rather than just using one?
They prove different things at different costs. UI tests are the only way to prove the rendered experience actually works for a real user, but they're slow and comparatively flaky — expensive to use for every possible data setup. API calls are fast and stable and are the efficient way to get the application into a specific state (seed 50 orders, create a user with a specific role) without clicking through forms repeatedly. The common pattern is seeding and authenticating via the API, then spending the (slower, costlier) UI test budget only on the specific flow that genuinely needs a browser.

Gotchas

to_be_ok() is a status check, not a body check It's satisfied by any 2xx status. A backend returning the wrong record, an empty list, or a stale cache with a 200 status all pass it — the body still needs its own, separate assertion.
Manually created contexts must be disposed A context from playwright.request.new_context() keeps a connection pool open until .dispose() is called. The api_request_context pytest fixture handles this automatically — leaving connections open across many manually-created contexts in a large suite is a real, if quiet, resource leak.
data= vs json= mix-ups Passing a Python dict as data= when the API expects a JSON body sends form-encoded data instead — the request still goes out and often still gets a response, just not the one the test expects, which can produce a confusing failure that looks unrelated to the actual cause.
page.request inherits the page's session — intentionally That's a feature for hybrid tests, but it's easy to forget: a call through page.request is authenticated as whatever the page is currently logged in as. If a test needs to hit the API as a different user, a standalone context with its own storage_state or headers is needed instead — reusing page.request there sends the wrong identity.
