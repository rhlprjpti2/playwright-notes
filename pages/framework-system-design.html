What this round actually evaluates

A technical screen asks "do you know how to use the tool." A design round asks "can you make defensible engineering trade-offs under ambiguous, incomplete requirements, and communicate them clearly." The interviewer usually cares less about which specific tool you land on than about how you got there — did you ask clarifying questions, did you consider constraints (team size, release cadence, existing tech debt), did you justify trade-offs, did you think about rollout and people, not just architecture.

The failure mode almost everyone falls into: hearing "design a test framework" and immediately describing Page Object Model and Playwright syntax. That answers a question nobody asked. The rest of this page works through one full example the way it should actually be handled.

The prompt

A realistic version of this question "You're joining as Lead SDET at a mid-size e-commerce company. 15 engineers, releasing to production daily. There's a web app, a mobile app, and roughly 40 backend microservices. The existing test suite is Selenium-based, takes 3 hours to run, and nobody trusts it — it's flaky enough that failures get re-run rather than investigated. Design the test automation strategy for the next two quarters."

Notice what's actually given: team size, release cadence, three different surfaces to test (web/mobile/API), and a specific, named pain point (flaky + slow + distrusted). Good answers use every one of those details. Weak answers ignore them and give a generic "here's my ideal framework" answer that would be identical regardless of the prompt.

Step 1: Clarify before designing

Before proposing anything, ask questions out loud. This is the single highest-signal move in the round — it demonstrates you don't design in a vacuum, and it often surfaces the actual constraint the interviewer wants you to discover.

  • What's the current test coverage split — how much is unit vs integration vs E2E today?
  • Is the 3-hour suite blocking every deploy, or is it a nightly/separate gate?
  • What's actually causing the flakiness — is it known (bad waits, shared test data, environment issues) or unexamined?
  • Is there budget/headcount for this, or is it "improve it with the team you already have"?
  • Any constraints already in place — existing CI tooling, cloud vs on-prem, compliance requirements?
An interviewer opens with "design a test framework for our platform" and gives no other detail. What's the strongest first move?

Step 2: The layered architecture

Once constraints are clear, lay out the framework as layers, not as a tool list. Each layer has a job and can be reasoned about independently — this is what separates "I'd use Playwright" from an actual architecture.

Interview framing Naming these layers explicitly — even briefly — signals architectural thinking in about 30 seconds. It's the fastest way to convert "I know Playwright" into "I can design a system."

Step 3: Test strategy & the pyramid

Given three surfaces (web, mobile, 40 microservices) and a distrusted 3-hour E2E suite, the strategic move is shifting weight down the pyramid, not just making the top layer faster.

LayerTarget proportionWhy, given this prompt
Unit~60-70%Fastest feedback, cheapest to maintain — should already exist per-service; if it doesn't, that's a finding worth stating.
Integration / API~20-30%40 microservices means most business logic is verifiable at the API layer without a browser at all — far cheaper than UI and catches most regressions.
E2E / UI~5-10%Reserved for genuine cross-service user journeys (checkout, login) — not every feature. This is where the 3-hour suite's real problem usually is: too much business logic pushed up into slow, flaky UI tests instead of tested at the API layer.

Stating a target ratio and explaining why — tied back to specifics in the prompt — is worth more than naming the pyramid as a concept everyone already knows.

Step 4: Scaling & the flaky-test problem

The prompt names flakiness as the actual pain point — a strong answer addresses it directly, not just implicitly through "using a better tool."

  • Diagnose before fixing. Categorize failures for two weeks: true regressions vs environment issues vs genuinely flaky tests vs bad test design. You can't fix what you haven't measured.
  • Quarantine, don't ignore. A test that fails intermittently gets tagged and moved to a non-blocking pipeline stage with a tracked ticket — not silently re-run until green, which is the exact behavior described in the prompt as the current failure mode.
  • Parallelize with isolated data. Sharding a suite across workers only helps if tests don't share mutable state — this is usually where "faster" attempts break correctness instead.
  • Track flakiness as a metric. A per-test flake rate, visible on a dashboard, turns "the suite is untrustworthy" from a vague feeling into a number you can drive toward zero and report on.

Step 5: CI/CD & quality gates

With a daily release cadence, the 3-hour suite is almost certainly blocking or slowing deploys. The design answer is staged gates, not one monolithic run:

  • Pre-merge (fast, blocking): unit + relevant integration tests for the changed service, minutes not hours.
  • Post-merge / pre-deploy (blocking): broader integration suite, sharded and parallelized.
  • Post-deploy smoke (blocking, fast): a small, hand-picked E2E set covering critical paths only — login, checkout — not the full regression suite.
  • Full regression (non-blocking, scheduled): the complete E2E suite runs nightly or on a schedule, feeding the flakiness dashboard, without sitting in the deploy path at all.
Common mistake Proposing to just "make the existing 3-hour suite faster" (more parallelization, bigger machines) without restructuring what runs where. That treats the symptom, not the cause — the prompt already tells you the suite isn't trusted even when it does finish.

Step 6: Rollout & team

This is the part almost every candidate skips, and it's exactly what distinguishes Lead-level from senior-IC-level answers: a design that can't actually be rolled out with a real team, mid-release-cadence, isn't a complete answer.

  • Incremental, not big-bang. You can't freeze a daily-release product for a framework rewrite. New tests get written against the new architecture; existing Selenium tests get migrated opportunistically or left running in parallel until coverage is proven equivalent.
  • Ownership model. Who owns framework core vs who writes test scripts — usually the platform/SDET team owns the former, feature engineers contribute the latter, with review standards enforced through code review, not tribal knowledge.
  • Define "done" early. Concrete exit criteria for the two-quarter window — e.g. suite runtime under 20 minutes for the blocking path, flake rate under 2%, X% of business logic covered at API level — turn a vague initiative into something reportable to stakeholders.

The reusable structure

The same six steps apply to almost any "design X" prompt this round throws at you — memorize the shape, not this specific answer:

  • 1. Clarify — constraints, current state, what's actually broken
  • 2. Architect in layers — scripts, framework core, driver/SDK, data/config, execution/reporting
  • 3. Strategy — where does coverage live (pyramid), and why given these constraints specifically
  • 4. Address the named pain directly — don't just describe an ideal system, solve the stated problem
  • 5. Pipeline design — staged gates, what blocks vs what doesn't
  • 6. Rollout & people — how this actually ships with a real team under real constraints

    • Other prompts you might get

    Same six-step structure applies to all of these — only the specifics change:

    • "Design a test strategy for a greenfield mobile app with no existing tests."
    • "Our end-to-end suite takes 6 hours and blocks every release — fix it."
    • "How would you introduce contract testing between 15 teams' microservices?"
    • "Design an automation strategy for a system you can't fully control the release cadence of (third-party integration heavy)."
    • "You've inherited a team of 5 SDETs and a framework nobody likes. What do you do in the first 90 days?" — a leadership variant of the same prompt, answered with the same structure plus people/process weighting.

    Interview Q&A

    Senior Walk me through how you'd design a test automation strategy for a new product from scratch.
    Start by clarifying constraints — team size, release cadence, surfaces to test, timeline. Then lay out the architecture in layers (test scripts, framework core, driver/SDK, data/config, execution/reporting) rather than naming tools first. Define a target test-pyramid ratio justified by the specifics given, design staged CI/CD gates (fast blocking pre-merge, broader blocking pre-deploy, non-blocking scheduled full regression), and close with rollout: how this gets built incrementally by a real team without freezing releases, plus concrete exit criteria.
    Senior A team says "our E2E suite is too flaky, let's just delete the flaky tests." How do you respond?
    Deleting flaky tests removes coverage along with the flakiness, trading a known problem for an unknown risk. Better: quarantine flaky tests into a non-blocking pipeline stage with tracked tickets, diagnose root cause (bad waits, shared mutable test data, genuine race conditions, or environment instability), and fix or rewrite based on that diagnosis. Track flake rate as a visible metric so "flaky" becomes measurable rather than a vibe. Only delete a test after confirming the behavior it covers is tested elsewhere.
    Scenario Leadership wants to cut the E2E suite runtime from 3 hours to 20 minutes in one sprint. What do you do?
    Push back on the timeline honestly while offering a real interim step. A structural fix (rebalancing the pyramid, moving logic to API-level tests) takes longer than one sprint to do safely. What's achievable fast: aggressive parallelization/sharding of the existing suite (if tests are independent), trimming the blocking path to a small critical-path smoke set while moving full regression to a non-blocking scheduled run, and quarantining known-flaky tests immediately. Frame it as "here's what closes the gap this sprint, here's the two-quarter plan for the rest" rather than either refusing or overpromising.
    Scenario You're the new Lead SDET and the team resents the current framework but leadership sees testing as a cost center, not an investment. How do you get buy-in for a rebuild?
    Lead with numbers leadership already cares about, not testing philosophy: current suite runtime, deploy frequency it's blocking, defect escape rate, engineer-hours lost to flaky-test investigation. Propose an incremental plan with measurable milestones rather than a "give me two quarters and trust me" rebuild — e.g. quarantine flaky tests this month (immediate stability win), rebalance pyramid on new features going forward (no big-bang risk), report flake-rate and runtime trend monthly. Buy-in follows visible, incremental proof, not an upfront pitch.
    Mid How do you decide what to automate vs what stays manual?
    Risk-based, not coverage-percentage-based: automate what's repeated often, high business impact if broken, and stable enough that the automation won't itself become high-maintenance churn. Exploratory testing, one-off validations, and UI still actively being redesigned are usually poor automation candidates early. The test pyramid ratio is a starting heuristic, not the actual decision criterion — the criterion is expected ROI per test.
    Mid What's the difference between Page Object Model and the Screenplay pattern, and when would you choose one over the other?
    POM models the UI — one class per page/component, encapsulating locators and actions. It's simple and well understood, and fine for small-to-mid frameworks. Screenplay models the user — actors with abilities performing tasks, composed from smaller interactions — which scales better for large frameworks with many user roles/journeys and encourages more reusable, composable test code, at the cost of more upfront design complexity. For a 15-engineer team building fresh, POM is usually the pragmatic choice; Screenplay earns its complexity at larger scale or with many distinct user personas.
    Senior How do you introduce contract testing (e.g. Pact) into an organization with 40 microservices and no existing practice?
    Don't roll it out everywhere at once — pick one high-traffic, frequently-changing consumer/provider pair with a known history of integration breakage as the pilot. Prove the value there (fewer integration incidents, faster feedback than full E2E) before expanding. Organizationally, contract tests need to live with the consumer team and run in the provider's CI as a required check — that ownership model has to be agreed on explicitly, or contracts rot unmaintained. Position it as replacing some brittle cross-service E2E coverage, not as additional work on top of it.
    Senior How would you measure whether a test automation investment is actually paying off?
    Track trends, not snapshots: suite runtime over time, flake rate, defect escape rate (bugs found in production that automation should have caught), time-to-feedback on a PR, and engineer-hours spent investigating false failures. The strongest ROI story ties a specific metric's improvement to a specific change you made — "flake rate dropped from 12% to 3% after quarantining and fixing the shared-test-data issue" is far more persuasive than "we now have 500 more tests."

    Gotchas

    Watch out Naming a tool in the first sentence ("I'd use Playwright with a POM framework...") before asking a single clarifying question is the single most common way candidates lose points in this round — it signals pattern-matching to a memorized answer rather than actual reasoning.
    Watch out Describing an architecture in the abstract without ever tying it back to the specific numbers/pain points given in the prompt (team size, release cadence, the named problem) reads as a generic rehearsed answer, not a response to this question.
    Watch out Stopping at architecture and skipping rollout/people entirely is the most common way to miss the "Lead" bar specifically — a senior IC can design a good architecture; a Lead has to also explain how it survives contact with a real team and real deadlines.
