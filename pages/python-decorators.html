The problem decorators solve

Say you want to time how long several different test-helper functions take, without pasting the same start/stop timing code into every single one of them. A decorator wraps a function with extra behavior — before, after, or instead of the original — while leaving the original function's own code completely untouched.

A decorator from scratch

A decorator is just a function that takes a function and returns a function — nothing more exotic than that, even though the syntax looks unusual the first time.

import time

def timed(func):
    def wrapper(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)
        elapsed = time.time() - start
        print(f"{func.__name__} took {elapsed:.2f}s")
        return result
    return wrapper

def load_dashboard(page):
    page.goto("https://example.com/dashboard")
    page.wait_for_selector(".widgets-loaded")

load_dashboard = timed(load_dashboard)   # manually "decorating" it
load_dashboard(page)                      # prints timing, then runs normally

Nothing here is decorator-specific syntax yet — it's just a function (timed) that takes load_dashboard as an argument and returns a different function (wrapper) that calls the original inside some extra logic. This is a closure — wrapper remembers func from its enclosing scope, exactly like the closures on Functions Deep Dive.

@ is just sugar

The @decorator syntax above a function definition is exactly equivalent to reassigning the function after defining it, the way the manual line above did — Python just gives it a cleaner spelling.

@timed
def load_dashboard(page):
    page.goto("https://example.com/dashboard")
    page.wait_for_selector(".widgets-loaded")

# ...is identical to...

def load_dashboard(page):
    page.goto("https://example.com/dashboard")
    page.wait_for_selector(".widgets-loaded")
load_dashboard = timed(load_dashboard)

functools.wraps

There's a real, common bug in the basic decorator above: after decorating, load_dashboard.__name__ is "wrapper", not "load_dashboard" — the original function's identity got hidden behind the wrapper. This breaks debugging output, introspection, and anything that reads __name__ or the docstring.

from functools import wraps

def timed(func):
    @wraps(func)          # copies __name__, __doc__, etc. from func onto wrapper
    def wrapper(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.time() - start:.2f}s")
        return result
    return wrapper

This is a one-line fix with no downside, which is why every decorator you'll see in real, well-written codebases uses @wraps(func) — omitting it is a small but genuine code-review flag.

Decorators that take arguments

A decorator with its own arguments — like @retry(times=3) — needs one more layer of nesting: a function that takes the arguments and returns a decorator.

def retry(times=3):
    def decorator(func):
        @wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    if attempt == times - 1:
                        raise
            return None
        return wrapper
    return decorator

@retry(times=5)
def click_flaky_button(page):
    page.click("#sometimes-slow-to-render")

Three layers, each with one job: retry(times=5) runs first and returns decorator; decorator receives the actual function and returns wrapper; wrapper is what finally executes on every call. It looks like a lot the first time, but each layer is doing exactly the same closure trick as the basic decorator, just one level deeper.

Stacking multiple decorators

@timed
@retry(times=3)
def load_dashboard(page):
    ...

Decorators apply bottom-up, closest-to-the-function first — so this is equivalent to timed(retry(times=3)(load_dashboard)). In practice: retry wraps the original function first, then timed wraps that result, so a call times the entire retry loop, not just one attempt. Order matters and swapping it changes behavior — worth tracing through deliberately rather than guessing.

Interview Q&A

Junior What is a decorator, in plain terms?
A function that takes another function as input and returns a new function — typically one that calls the original but adds behavior before, after, or around it (timing, logging, retrying, access control). The @decorator syntax above a function definition is shorthand for reassigning the function to the decorator's return value.
Mid What problem does functools.wraps solve, and what breaks without it?
A decorator normally returns a new inner function ("wrapper") in place of the original — so without intervention, the decorated function's __name__, docstring, and other metadata get replaced by the wrapper's, not the original function's. @wraps(func) copies that metadata from the original function onto the wrapper, so introspection, debugging output, and documentation tools still see the original function's identity rather than a generic "wrapper".
Mid Why does a decorator that accepts arguments (like @retry(times=3)) need an extra layer of nesting compared to a plain decorator?
A plain decorator like @timed is just timed(func) — one function call. But @retry(times=3) is evaluated as retry(times=3) first (which must return the actual decorator), and only then is that result called with the function: retry(times=3)(func). So retry itself isn't the decorator — it's a factory that takes the configuration arguments and returns the real decorator function, adding one layer of nesting versus a plain decorator.
Senior When multiple decorators are stacked on one function, what order do they run in, and why does it matter?
They apply bottom-up (closest to the function first) but execute top-down on each actual call. @a @b def f() means f = a(b(f)) — b wraps the original first, then a wraps b's result. On a call, a's wrapper runs first (since it's the outermost layer), and it decides whether/when to call into b's wrapper, which then decides whether/when to call the original. Order changes real behavior: stacking a timing decorator outside a retry decorator measures the entire retry loop's duration; swapping the order would measure only the final successful attempt.

Gotchas

Forgetting @wraps silently breaks introspection The decorated function still runs correctly — the bug is invisible until something reads __name__, a docstring, or a stack trace, and gets the wrapper's identity instead of the real function's.
A decorator without *args, **kwargs only works on functions with that exact signature def wrapper(x): instead of def wrapper(*args, **kwargs): means the decorator silently breaks the moment it's applied to a function with a different parameter list. Always forward with *args, **kwargs unless the decorator is deliberately built for one specific signature.
