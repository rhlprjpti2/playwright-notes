Dynamic Web Tables

"Verify the price of Rice is 37" sounds trivial until you can't assume which column price is in, or which row Rice is on. This is the classic table interview question, and the answer is a chain of concepts — count, loops, filter, nth, scoped search — combined rather than any single API.

The problem

Given a table of products and prices, verify that Rice costs 37. The naive approach — td:nth-child(2) on row 4 — works exactly until someone adds a column, re-sorts the rows, or inserts a product. Both coordinates are unknown at write-time:

  • Which column holds the price? Columns can be added or reordered.
  • Which row holds Rice? Rows are dynamic and may be sorted differently.

So the solution has three parts: find the price column index at runtime, find the Rice row at runtime, then read the cell where they intersect.

The full solution

page.goto(TABLE_URL)

# 1. Find which column holds "Price" — don't assume it's column 2
price_column = -1
column_count = page.locator("th").count()

for i in range(column_count):
    if page.locator("th").nth(i).filter(has_text="Price").count() > 0:
        price_column = i
        print(f"Price column index is {price_column}")
        break

# 2. Find the Rice row by content, not position
rice_row = page.locator("tr").filter(has_text="Rice")

# 3. Read the cell where they intersect, scoped to that row
expect(rice_row.locator("td").nth(price_column)).to_have_text("37")
The f-string f"Price column index is {price_column}" — prefixing a string with f makes anything inside {} evaluate as a variable at runtime rather than print literally. Without the f, you'd get the text {price_column} printed as-is.

The APIs involved

APIWhat it does here
.count()Returns how many elements a locator matched, as a plain number you can loop over. Distinct from expect(...).to_have_count(n), which asserts rather than returns.
.nth(i)Selects the element at index i from a multi-match locator. Legitimate here because the index is computed at runtime, not hardcoded.
.filter(has_text=...)Narrows a locator to elements containing given text — the mechanism for finding both the column and the row by content.
scoped locator()Calling .locator() on an existing locator searches only inside it. See Dynamic Locators for the same pattern on product cards.
to_have_text()Asserts exact text. Use to_contain_text() when you only need a substring match.
Beyond this video — a shorter route when the DOM cooperates If the table has proper semantic markup, Playwright's ARIA roles can do a lot of this directly: page.get_by_role("row").filter(has_text="Rice").get_by_role("cell").nth(price_column). And for the column lookup, page.locator("th").all_text_contents() returns a plain Python list of every header's text in one call, so you can use .index("Price") instead of a manual loop. The loop version above is worth understanding because it's what an interviewer usually wants to see you reason through — but knowing the shortcut shows depth.

Interview Q&A

Mid How would you verify a specific cell's value in a table where both the row and column positions are dynamic?
Resolve both coordinates at runtime. For the column: get all th elements, use count() as a loop bound, and check each with .nth(i).filter(has_text="Price").count() > 0, recording the index and breaking on match. For the row: page.locator("tr").filter(has_text="Rice") — content-based, so position doesn't matter. Then intersect: rice_row.locator("td").nth(price_column), scoping the cell search to that row. Finally assert with expect(...).to_have_text().
Junior What's the difference between .count() and expect(locator).to_have_count(n)?
.count() returns a number you can use in code — as a loop bound, in an if-condition, anywhere. to_have_count(n) is a web-first assertion: it doesn't return anything usable, it auto-retries until the count matches or fails the test. Use count() for logic, to_have_count() for verification.
Mid Earlier you said hardcoding .nth() is fragile. Why is it acceptable here?
Because the index isn't hardcoded — it's computed at runtime by scanning the headers. nth(price_column) where price_column was discovered by searching for the text "Price" is fundamentally different from nth(1) written by hand. The fragility of .nth() comes from assuming a fixed position, not from the method itself.
Scenario Your table test passes locally but fails in a different environment where the table has an extra "Stock" column inserted before Price. Does this solution survive?
Yes — that's precisely what it's built for. The column loop rescans headers at runtime, so Price simply resolves to index 2 instead of 1, and everything downstream adjusts. A hardcoded nth(1) would silently read the Stock value and either fail with a confusing mismatch or, worse, pass against the wrong data.
Senior Is looping through headers in Python the best approach, or is there a more idiomatic Playwright way?
The loop is explicit and easy to reason about, which is why it's good for demonstrating the logic. More idiomatic options: page.locator("th").all_text_contents() returns every header's text as a Python list in one round-trip, so .index("Price") replaces the whole loop — fewer calls to the browser and simpler code. If the markup is semantic, get_by_role("row")/get_by_role("cell") is more robust than tag selectors. Worth noting the loop makes one browser round-trip per header, which matters on large tables.

Gotchas

Scope is the bug that bites page.locator("td").nth(price_column) searches every cell in the table — with 5 rows of 3 columns that's 15 cells, so nth(1) returns the first row's price, not Rice's. The scoped form rice_row.locator("td") is what makes the index mean "column within this row."
Substring matching in filters filter(has_text="Rice") matches any row containing that text — a row for "Brown Rice" or "Rice Flour" would also match, and a multi-match locator then fails strict mode. When values can overlap, filter on an exact-match regex or a more specific cell locator instead.
