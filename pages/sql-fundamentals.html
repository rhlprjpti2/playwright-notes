SQL Fundamentals & Command Categories

Concept

SQL is a declarative language — a query says what result is wanted, not the step-by-step procedure to produce it. That's the whole reason a query optimizer can exist at all: the same SELECT can be satisfied by wildly different execution strategies (a full table scan vs. an index lookup) and the query itself never has to say which one to use. Everything else on this page follows from that one fact.

The trap inside this question DDL statements (CREATE, ALTER, DROP, TRUNCATE) implicitly commit in most databases — they can't be rolled back inside a transaction the way DML can. Someone who says "just wrap it in a transaction and roll back if the test fails" without knowing this will run into a schema change that silently stuck around.

Logical query execution order

The single most useful mental model in this entire track. A query is written top to bottom as SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT — but the database doesn't run it in that order. It's actually processed like this:

Written orderActual execution order
1. SELECT1. FROM (+ JOIN)
2. FROM2. WHERE
3. WHERE3. GROUP BY
4. GROUP BY4. HAVING
5. HAVING5. SELECT
6. ORDER BY6. ORDER BY
7. LIMIT7. LIMIT

This single table answers a whole cluster of "why does SQL do this" questions in one shot:

  • Why can't WHERE use an aggregate like COUNT(*)? Because WHERE (step 2) runs before GROUP BY (step 3) — there's no group to aggregate yet. HAVING (step 4) exists specifically because it runs after grouping.
  • Why can't WHERE reference a column alias defined in SELECT? Because SELECT is step 5 — the alias doesn't exist yet at step 2.
  • Why can ORDER BY reference a SELECT alias? Because ORDER BY is step 6, after SELECT has already run.
SELECT customer_id, COUNT(*) AS order_count FROM orders WHERE order_count > 5 GROUP BY customer_id; — why does this fail?

SELECT, WHERE, ORDER BY

The baseline shape every other topic in this track builds on:

SELECT first_name, last_name, hire_date
FROM employees
WHERE department = 'Engineering'
ORDER BY hire_date DESC;

WHERE filters individual rows before any grouping happens (see the execution-order model above). ORDER BY defaults to ascending (ASC); DESC reverses it. Multiple columns are allowed and evaluated left to right — ORDER BY department, hire_date DESC sorts by department first, then by hire date within each department group.

DISTINCT, LIMIT/OFFSET

SELECT DISTINCT department FROM employees;        -- unique departments only

SELECT * FROM employees
ORDER BY hire_date DESC
LIMIT 10;                                          -- most recent 10 hires

SELECT * FROM employees
ORDER BY hire_date DESC
LIMIT 10 OFFSET 10;                                -- the *next* 10 — page 2
Pagination needs a stable ORDER BY Without an explicit, unique ORDER BY, row order is not guaranteed between two separate queries — LIMIT/OFFSET pagination can silently skip or repeat rows across pages if the sort isn't deterministic. This is a real bug class, not just a theoretical concern, and worth mentioning if asked about pagination reliability.

NULL handling

NULL means "unknown," not "empty" or "zero" — and that changes how comparisons behave in a way that catches almost everyone at least once.

SELECT * FROM employees WHERE manager_id = NULL;    -- returns ZERO rows, always
SELECT * FROM employees WHERE manager_id IS NULL;   -- this is the correct form

SELECT COALESCE(nickname, first_name) AS display_name FROM employees;  -- first non-null value
SELECT NULLIF(discount, 0) AS discount FROM orders;                    -- NULL if the two are equal

manager_id = NULL doesn't evaluate to false — it evaluates to NULL (unknown), and a WHERE clause only keeps rows where the condition is true. NULL is neither kept nor rejected as false; it's simply never true, so the row is dropped either way. This is three-valued logic (true / false / unknown), not the two-valued boolean logic most languages use.

NULL breaks NOT IN silently WHERE id NOT IN (SELECT manager_id FROM employees) returns zero rows if even one manager_id in that subquery is NULL — not an error, just silently wrong. NOT IN against a list containing NULL can never be proven true for anything, by the same three-valued-logic rule above. NOT EXISTS is the safer, NULL-proof alternative for this pattern.

CASE WHEN

Inline conditional logic inside a query — the closest thing SQL has to an if/elif/else expression, and commonly used to bucket rows into categories without a separate lookup table:

SELECT
  order_id,
  total,
  CASE
    WHEN total >= 1000 THEN 'high'
    WHEN total >= 100  THEN 'medium'
    ELSE 'low'
  END AS order_tier
FROM orders;

Evaluated top to bottom, first match wins — the exact same short-circuit behavior as a Python if/elif/else chain. ELSE is optional; if it's omitted and nothing matches, the result is NULL rather than an error.

Data types, briefly

Deep type-system trivia rarely comes up — but a few distinctions are common enough to be worth knowing cold:

ChoiceWhat actually matters
VARCHAR(n) vs CHAR(n)CHAR is fixed-width, space-padded; VARCHAR is variable-length. Default to VARCHAR unless every value is genuinely the same length (e.g. a 2-letter country code).
DECIMAL/NUMERIC vs FLOATFLOAT is binary floating-point and loses precision — never use it for money. DECIMAL(p,s) stores an exact value and is the correct choice for currency.
DATE vs TIMESTAMPDATE is calendar-date only; TIMESTAMP includes time (and often timezone, depending on the database).

Interview Q&A

Junior What's the difference between DDL, DML, DCL, and TCL?
DDL (CREATE/ALTER/DROP/TRUNCATE) changes schema structure and auto-commits. DML (SELECT/INSERT/UPDATE/DELETE) changes or reads row data. DCL (GRANT/REVOKE) manages permissions. TCL (COMMIT/ROLLBACK/SAVEPOINT) controls transaction boundaries around DML.
Mid Why does a query fail when a WHERE clause tries to filter on an aggregate function?
Because of logical execution order: WHERE runs before GROUP BY, so no aggregation has happened yet at that point — there's nothing for an aggregate function to aggregate. HAVING exists specifically to filter after grouping, once aggregates are available.
Mid Why does WHERE id = NULL never return any rows, even when id genuinely has no value?
SQL uses three-valued logic — a comparison against NULL evaluates to NULL (unknown), not true or false. WHERE only keeps rows where the condition is true, and NULL never satisfies that, so the row is dropped regardless of the actual data. IS NULL is a dedicated operator built for this case and is the only correct way to test for NULL.
Mid Can ORDER BY reference a column alias defined in SELECT? Can WHERE?
ORDER BY can — it's step 6 in logical execution order, after SELECT (step 5) has already produced that alias. WHERE cannot — it's step 2, long before SELECT runs, so the alias doesn't exist yet from WHERE's point of view.
Senior A teammate wraps a schema migration in a transaction "to be safe" and rolls it back after a test failure — but the schema change is still there. Why?
DDL statements auto-commit in most databases (notably MySQL) and can't be rolled back as part of a transaction the way DML can. Some databases (PostgreSQL) do support transactional DDL, so this is engine-dependent — but the safe assumption in an interview, and in practice, is that a DROP/ALTER/CREATE should be treated as immediately permanent rather than relying on ROLLBACK as a safety net.
Senior Why does WHERE id NOT IN (subquery) sometimes return zero rows unexpectedly?
If the subquery's result set contains even one NULL, NOT IN can never be proven true for any row, by the same three-valued-logic rule that breaks direct NULL comparisons — so the whole query silently returns nothing rather than erroring. NOT EXISTS is NULL-safe and is the recommended alternative whenever the subquery's column might contain NULL.

Gotchas

DDL auto-commits — no rollback safety net Treat schema changes as immediately permanent in most engines, regardless of surrounding transaction code.
= NULL is always wrong It silently returns zero rows instead of erroring, which makes it a genuinely dangerous typo — no test failure points at the real cause. Always IS NULL / IS NOT NULL.
NOT IN plus a NULL-containing subquery = silently empty Prefer NOT EXISTS whenever the subquery's column could contain NULL — which, without an explicit NOT NULL constraint, should be the default assumption.
Unstable pagination LIMIT/OFFSET without a fully deterministic ORDER BY (unique column, or a tiebreaker added to a non-unique one) can skip or duplicate rows across pages if the underlying data changes between queries.
