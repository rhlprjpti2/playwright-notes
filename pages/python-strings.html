String Methods for Automation

More automation code touches strings than any other type — extracting an ID from a URL, cleaning scraped text, building a locator dynamically. This page is the method toolkit; the split()/strip() bug walkthrough already on this site is the worked example of what goes wrong when you don't know it well.

Strings are immutable

Every method on this page returns a new string — none of them modify the original in place, because str is immutable (see Memory Model). This trips people who expect .strip() to clean up a variable directly:

text = "  hello  "
text.strip()          # returns "hello" — but text itself is unchanged!
print(text)            # "  hello  " — still has the spaces

text = text.strip()   # this is what you actually want — rebind the name
print(text)             # "hello"
The single most common string bug Calling a string method for its side effect, as if strings were mutable like lists. There is no side effect — every method is read-only and returns a new object. If you don't capture the return value, nothing happens to your variable.

Slicing

string[start:stop:step] — the single most-used piece of string syntax, and the one that trips people up with negative indices and off-by-one boundaries.

s = "Playwright"
s[0]        # 'P'          — single character
s[0:4]      # 'Play'       — index 4 is EXCLUDED (stop is exclusive)
s[-1]       # 't'          — negative indices count from the end
s[-6:]      # 'wright'     — from index -6 to the end
s[::2]      # 'Pywih'      — every 2nd character
s[::-1]     # 'thgirwyalP' — step -1 reverses the whole string
Reading a slice out loud s[a:b] reads as "start at index a, stop before index b." The length of the result is always b - a. Omitting a means "from the start"; omitting b means "to the end."

f-strings

The modern, preferred way to build a string from variables — a literal prefixed with f, where anything inside {} is evaluated as code rather than printed as text (this exact mechanism is already used in the Web Tables page's f"Price column index is {price_column}"):

name = "Rice"
price = 37
f"{name} costs {price}"          # "Rice costs 37"
f"{name} costs {price:.2f}"      # "Rice costs 37.00"  -- format spec after the colon
f"{price * 1.1:.2f}"              # "40.70" -- any expression works, not just variable names

Predates f-strings and still common in older code: "{} costs {}".format(name, price) and the oldest style, "%s costs %s" % (name, price). All three produce identical output — f-strings are simply more readable and slightly faster, so prefer them in new code, but expect to read the older styles in existing codebases.

When methods aren't enough: re

String methods handle fixed, known delimiters well. When the pattern is more flexible — "an email-shaped substring somewhere in this text," not "the text after the word 'at'" — that's what the re module is for:

import re

text = "Contact us at support@shop.example.com for help"
match = re.search(r"[\w.+-]+@[\w-]+\.[\w.-]+", text)
if match:
    print(match.group())   # "support@shop.example.com"

This is genuinely more robust than the split("at") approach used elsewhere on this site — it doesn't depend on the word "at" appearing in the sentence at all, just on an email-shaped pattern existing somewhere in the text. The tradeoff is readability: regex is powerful but a lot less self-explanatory than chained string methods, so many teams reserve it for cases where simple methods genuinely can't express the pattern.

Beyond this page — regex is a full topic on its own This is intentionally the shallow end. re.search() (first match), re.findall() (all matches), re.match() (anchored to the start only), and re.sub() (find-and-replace by pattern) cover most automation needs. A dedicated regex page is a reasonable future addition to this section if it comes up often enough in practice.

Interview Q&A

Junior Why doesn't calling `.strip()` on a variable change it?
Strings are immutable — every string method returns a new string rather than modifying the original in place. Calling text.strip() without capturing the result discards the cleaned string; you need text = text.strip() to actually update the variable.
Junior What's the difference between .find() and .index()?
Both return the position of the first occurrence of a substring. .find() returns -1 if the substring isn't found; .index() raises a ValueError instead. Use .find() when "not found" is a normal, expected outcome you'll handle; use .index() when not finding it should be treated as an error.
Mid What does `s[2:-1]` do?
Starts at index 2 and stops before the last character (index -1 is the last character, and the stop bound is exclusive) — so it returns everything from index 2 up to, but not including, the final character. Mixing positive start and negative stop indices like this is common when trimming a known prefix and an unknown-length suffix in one slice.
Scenario You need to extract a numeric ID from URLs that sometimes end in a trailing slash and sometimes don't. Why is string splitting fragile here, and what's more robust?
A fixed approach like url.split("/")[-1] breaks the moment a trailing slash is present — the last split segment becomes an empty string instead of the id. More robust: strip trailing slashes first (url.rstrip("/")) before splitting, or use a regex anchored to digits at the end (re.search(r"(\d+)/?$", url)), which tolerates the optional trailing slash by design rather than by a defensive preprocessing step.
Mid When would you reach for regex instead of chained string methods?
When the thing you're matching is a pattern rather than a fixed, known delimiter — validating an email shape, extracting all numbers from free text, matching one of several possible formats. String methods like split()/find() work well when you know exactly what surrounds your target text; regex is the right tool when what surrounds it varies but the target itself has a recognizable shape.

Gotchas

split() with no separator behaves differently than split(" ") "a b".split() (no argument) treats runs of any whitespace as one delimiter and returns ['a', 'b']. "a b".split(" ") (explicit space) splits on every single space character and returns ['a', '', 'b'] — the double space produces an empty string in the middle. These are not interchangeable, and the difference is exactly the kind of thing that silently breaks a script when input has inconsistent spacing.
String concatenation in a loop is O(n²) result = ""; for x in big_list: result += x creates a new string object on every iteration (strings are immutable), copying everything accumulated so far each time. For large loops, build a list and "".join(list) at the end instead — one allocation instead of one per iteration.
