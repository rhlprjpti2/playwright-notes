Subqueries & Set Operations

Correlated vs non-correlated is really a performance question wearing a syntax costume — a correlated subquery re-runs once per outer row, which either doesn't matter or matters enormously depending on table size. Plus UNION's silent deduplication and CTEs as subqueries you can actually read.

Concept

A subquery is a query nested inside another — in WHERE, in SELECT, in FROM. The distinction that actually matters in an interview isn't where it's nested, it's whether it references anything from the outer query: non-correlated subqueries stand alone and run once; correlated subqueries reference an outer-query column and conceptually re-run once per outer row.

Non-correlated subqueries

Fully self-contained — nothing inside it references anything from the outer query, so it can run completely on its own first, and the outer query just uses whatever it returned:

-- The inner query runs exactly ONCE, independent of the outer query,
-- producing one fixed number the outer query then compares every row against
SELECT name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);   -- one company-wide average, computed once

Run the inner query by itself in a separate tab and it returns a perfectly normal single value — that's the tell for non-correlated: it doesn't need the outer query to mean anything at all. Compare that to the correlated example below, where the inner query references e1.department and can't run standalone.

This is the performance conversation, not just a syntax detail On a 4-row table, re-running the inner query 4 times is free. On a million-row table, a correlated subquery can mean a million re-executions of the inner query — often the actual root cause when someone says "this query used to be fast." Many databases' optimizers can rewrite some correlated subqueries into an equivalent join internally, but that's an optimization, not a guarantee — understanding what the naive execution looks like is what the interview question is really testing.

EXISTS vs IN

-- IN — compares against a full list of values
SELECT * FROM customers WHERE id IN (SELECT customer_id FROM orders);

-- EXISTS — just checks whether the correlated subquery returns anything at all
SELECT * FROM customers c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

UNION vs UNION ALL

Both stack the rows from two queries on top of each other — the entire difference is whether the result is deduplicated afterward:

SELECT name FROM engineers
UNION
SELECT name FROM managers;        -- "Ada" appearing in both lists shows up ONCE

SELECT name FROM engineers
UNION ALL
SELECT name FROM managers;        -- "Ada" appearing in both lists shows up TWICE
Default to UNION ALL unless duplicates are actually a problem Deduplication isn't free — UNION has to sort or hash the entire combined result to find and remove duplicates. If the two queries are already known not to overlap (or duplicates are fine), UNION ALL is strictly cheaper.

INTERSECT and EXCEPT

OperatorReturns
INTERSECTOnly rows present in both query results — e.g. employees who are both managers and certified trainers.
EXCEPT (MINUS in Oracle)Rows in the first query's result that do not appear in the second — e.g. customers who signed up but never placed an order.

Both, like UNION, require the two queries to select the same number of columns with compatible types — this is a shared syntactic rule across all set operations, not specific to any one of them.

CTEs — subqueries with a name

A Common Table Expression (WITH) is a named, temporary result set that can be referenced later in the same query — functionally similar to a subquery, but readable top to bottom instead of nested inside itself:

-- Nested subquery — reads inside-out
SELECT name FROM (
  SELECT customer_id, COUNT(*) AS order_count
  FROM orders
  GROUP BY customer_id
) AS order_counts
JOIN customers ON customers.id = order_counts.customer_id
WHERE order_count > 5;

-- Same logic as a CTE — reads top to bottom
WITH order_counts AS (
  SELECT customer_id, COUNT(*) AS order_count
  FROM orders
  GROUP BY customer_id
)
SELECT name
FROM order_counts
JOIN customers ON customers.id = order_counts.customer_id
WHERE order_count > 5;

Multiple CTEs can be chained with commas, each one able to reference the ones defined before it — which is how a long, multi-stage transformation stays readable instead of turning into several layers of nested parentheses.

Recursive CTEs

A CTE that references itself, used for hierarchical or graph-shaped data where the depth isn't known in advance — an org chart, a category tree, a bill-of-materials. Each iteration adds one more level:

WITH RECURSIVE org_chain AS (
  -- Anchor: the starting row(s), no recursion yet
  SELECT id, name, manager_id, 1 AS depth
  FROM employees WHERE id = 1                 -- start at the CEO

  UNION ALL

  -- Recursive step: join back to org_chain itself, one level at a time
  SELECT e.id, e.name, e.manager_id, oc.depth + 1
  FROM employees e
  JOIN org_chain oc ON e.manager_id = oc.id
)
SELECT * FROM org_chain;
An infinite recursive CTE is a real, self-inflicted incident If the data has a cycle (A manages B, B manages A — a data-integrity bug, but it happens) or the recursive step's join condition is wrong, the query never reaches zero new rows and runs until the database's recursion limit or timeout kills it.

Interview Q&A

Junior What's the difference between a correlated and non-correlated subquery?
A non-correlated subquery is fully independent of the outer query and conceptually runs once. A correlated subquery references a column from the outer query, so it conceptually re-runs once per outer row — the inner query's result can be different for every row being checked.
Mid When would you prefer EXISTS over IN?
EXISTS is NULL-safe and typically the better default for existence checks, especially against large tables — it only needs to confirm at least one matching row exists rather than materializing a full list. IN (or specifically NOT IN) becomes dangerous when the subquery's result can contain NULL, since NOT IN against a NULL-containing list silently returns zero rows.
Mid What's the actual difference between UNION and UNION ALL?
UNION deduplicates the combined result — any row appearing in both queries shows up once. UNION ALL keeps every row from both queries, including duplicates, and is cheaper since it skips the sort/hash step needed to find duplicates.
Mid What problem do CTEs solve that a regular subquery doesn't?
CTEs don't add new capability over an equivalent nested subquery in most cases — the improvement is readability. A WITH clause reads top to bottom and can be referenced by name later in the query, versus a nested subquery that reads inside-out and gets harder to follow as nesting depth increases. Multiple CTEs can also reference earlier ones, turning a multi-stage transformation into a readable sequence instead of layered parentheses.
Senior How does a recursive CTE know when to stop?
It re-runs its recursive member against the CTE's own growing result set, each time joining only against rows added in the previous iteration, until a run produces zero new rows — at that point the recursion terminates naturally. If the underlying data has a cycle, or the join condition is wrong, that zero-new-rows state is never reached and the query runs until the database's recursion depth limit or a timeout stops it.

Gotchas

Correlated subqueries can silently be O(n²) Fine on small tables, a real performance cliff on large ones — this is a legitimate root cause to investigate for "this query got slow" incidents.
NOT IN plus a NULL-containing list Covered in Fundamentals, worth repeating here since subqueries are the most common source of it: prefer NOT EXISTS whenever the subquery's column could contain NULL.
An unbounded recursive CTE Always sanity-check that the recursive step's join condition actually converges toward zero new rows — a cyclic data relationship or a wrong join condition means it never does.
