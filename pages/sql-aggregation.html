Aggregation & Grouping

GROUP BY collapses many rows into one per bucket — the mechanics of exactly how that collapse happens, and the COUNT(*) vs COUNT(column) distinction that trips up almost everyone the first time NULL enters the picture.

Concept

GROUP BY takes rows that share a value in one or more columns and collapses each group into a single output row — and every column in SELECT that isn't part of the grouping has to go through an aggregate function (COUNT, SUM, AVG, MIN, MAX), because there's no longer a single row's value to show — there's a whole group of them.

GROUP BY, row by row

Five real order rows, bucketed by customer, with two aggregates computed per bucket at once:

One output row per distinct value, always It doesn't matter whether a bucket has 1 row or 100 — GROUP BY always collapses it to exactly one row in the result. This is the entire reason ungrouped columns need an aggregate function: SELECT customer_id, amount FROM orders GROUP BY customer_id is invalid in strict SQL mode, because amount could be any one of several different values within a bucket, and the database has no rule for picking which.

AVG, MIN, MAX

Same bucketing mechanics as the COUNT/SUM stepper above — each aggregate function just computes something different across the rows in a bucket:

SELECT customer_id,
       COUNT(*)     AS order_count,
       SUM(amount)  AS total_spent,
       AVG(amount)  AS avg_order_value,
       MIN(amount)  AS smallest_order,
       MAX(amount)  AS largest_order
FROM orders
GROUP BY customer_id;

For customer 1's two orders ($40, $60) from the stepper above: COUNT(*) = 2, SUM = 100, AVG = 50, MIN = 40, MAX = 60. All six aggregate functions can run in the same SELECT simultaneously — each one just does its own pass over the same grouped rows.

AVG on integer columns can silently truncate In some databases, AVG() over an integer column returns an integer, truncating the decimal — three orders of $10, $10, $11 average to 10.33, but a truncating AVG reports 10. Casting to a decimal/float type before averaging (AVG(amount::numeric) in Postgres, AVG(CAST(amount AS DECIMAL)) more portably) avoids losing that precision.

COUNT(*) vs COUNT(column)

COUNT(*) counts rows. COUNT(column) counts non-NULL values in that column — and the two give different answers the moment any row has a NULL in that column.

-- orders: 5 rows total, but 'notes' is NULL on 2 of them
SELECT COUNT(*) FROM orders;          -- 5 (every row counts)
SELECT COUNT(notes) FROM orders;      -- 3 (NULLs are skipped)
The trap this creates A dashboard reporting "3 orders have notes" using COUNT(notes) and "5 total orders" using COUNT(*) in the same query is correct, not buggy — but a developer who doesn't know the distinction will "fix" what looks like a mismatched number, or worse, use COUNT(column) everywhere out of habit and silently undercount whenever that column has NULLs.

HAVING vs WHERE, revisited

Covered in Fundamentals as an execution-order consequence — worth restating directly here since it's specifically an aggregation topic: WHERE filters individual rows before grouping; HAVING filters entire groups after aggregation has already happened.

-- Keep only customers with more than 1 order — a group-level condition, needs HAVING
SELECT customer_id, COUNT(*) AS order_count
FROM orders
GROUP BY customer_id
HAVING COUNT(*) > 1;

-- Both together — WHERE narrows the rows first, HAVING narrows the resulting groups
SELECT customer_id, COUNT(*) AS order_count
FROM orders
WHERE amount > 10
GROUP BY customer_id
HAVING COUNT(*) > 1;

Grouping by more than one column

SELECT customer_id, status, COUNT(*) AS count
FROM orders
GROUP BY customer_id, status;

Each distinct combination of customer_id and status becomes its own group — a customer with both shipped and pending orders gets two separate result rows, one per status, not one row averaged across both.

A table has 3 customers, each with orders in exactly 2 different statuses. How many rows does GROUP BY customer_id, status return?

Interview Q&A

Junior What's the difference between COUNT(*) and COUNT(column_name)?
COUNT(*) counts every row, regardless of content. COUNT(column_name) counts only rows where that specific column is non-NULL — any row with a NULL in that column is skipped. They return the same number only when the column has no NULLs at all.
Junior Why can't you SELECT a non-aggregated, non-grouped column alongside GROUP BY?
Because GROUP BY collapses potentially many rows into one output row per group, and an ungrouped column could hold different values across the rows in that group — there's no defined rule for which one to display. Every selected column must either be part of the GROUP BY list or wrapped in an aggregate function that reduces the group to one value.
Mid Write a query to find customers with more than 2 orders.
SELECT customer_id, COUNT(*) FROM orders GROUP BY customer_id HAVING COUNT(*) > 2; — WHERE can't be used here because COUNT(*) doesn't exist until after grouping; the filter has to be HAVING.
Senior A report shows "150 total signups" from COUNT(*) but "142 signups with a referral source" from COUNT(referral_source) on the same table. A stakeholder flags this as a bug. How do you respond?
It's expected behavior, not a bug — COUNT(*) counts all 150 rows regardless of content, while COUNT(referral_source) only counts the 142 rows where that column is non-NULL. The gap of 8 represents signups with no recorded referral source. Worth proactively clarifying this distinction in the report itself, since it's exactly the kind of number mismatch that reads as a data-quality bug to someone unfamiliar with how COUNT handles NULLs.

Gotchas

COUNT(column) silently undercounts when NULLs exist Default to COUNT(*) for "how many rows" questions; reach for COUNT(column) only when the question is specifically "how many rows have a value here."
WHERE on an aggregate is a syntax error, not a slow query WHERE COUNT(*) > 1 fails outright — the aggregate doesn't exist yet at WHERE's point in execution order. It has to be HAVING.
Every non-aggregated SELECT column must be in GROUP BY Some databases (older MySQL configurations) silently allow this and pick an arbitrary row's value; most (PostgreSQL, strict MySQL) reject it outright. Never rely on the permissive behavior even where it's allowed — the "arbitrary" row it picks isn't guaranteed to stay consistent.
