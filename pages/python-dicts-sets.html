Dicts & Sets

A dict is how you'll store almost every piece of structured test data — API responses, expected-vs-actual comparisons, config. The reason it feels instant no matter how big it gets is a specific mechanism worth actually understanding.

Creating & accessing

response = {"status": "passed", "duration_ms": 342, "retries": 0}
response["status"]          # "passed"
response["missing_key"]     # KeyError — raises immediately
response.get("missing_key") # None — no error
response.get("retries", 0)  # 0 — explicit default if key is absent

.get() is the safer default for anything that might not exist — API responses, optional test config — while plain [] indexing is the right call when a missing key genuinely means something is broken and should fail loudly.

Why dict lookups are O(1)

A list stores items in order — checking x in my_list means scanning from the start until Python finds a match or runs out of items, an O(n) operation that gets slower as the list grows. A dict works completely differently under the hood.

listdict / set
Storageordered sequencehash table — key's hash determines its bucket directly
x in collectionO(n) — scans until foundO(1) average — hash(x) jumps straight to the bucket
Requirementnonekeys must be hashable (immutable)

This is why if value in some_set is the idiomatic way to check membership against a large collection in automation code — checking against a set of a few thousand expected IDs stays fast, where the same check against a list would visibly slow down as the list grows.

expected = {"status": "passed"}
actual = {"status": "passed", "duration_ms": 120}
merged = expected | actual   # {"status": "passed", "duration_ms": 120}
Dicts remember insertion order Since Python 3.7 this is a guaranteed language feature, not an implementation detail — iterating a dict always yields keys in the order they were first inserted. Useful to know, but don't rely on it for anything that needs true sorting; sort explicitly with sorted(d.items()) when order matters semantically.

Dict comprehensions

results = [("test_login", "passed"), ("test_logout", "failed")]

# Manual loop
status_map = {}
for name, status in results:
    status_map[name] = status

# Equivalent comprehension
status_map = {name: status for name, status in results}

# With a filter
failures = {name: status for name, status in results if status == "failed"}

Sets

A set is an unordered collection of unique, hashable values — written {1, 2, 3} or built via set(iterable). Its two jobs: deduplicating, and fast membership checks (same O(1) hashing as dicts).

expected_ids = {101, 102, 103}
actual_ids = {102, 103, 104}

expected_ids | actual_ids   # union: {101, 102, 103, 104}
expected_ids & actual_ids   # intersection: {102, 103}
expected_ids - actual_ids   # difference: {101}  — expected but not actual
expected_ids ^ actual_ids   # symmetric difference: {101, 104} — in exactly one

That - and ^ pair is genuinely useful in test automation: comparing an expected set of IDs against what actually came back from an API tells you exactly what's missing and what's unexpectedly extra, in two expressions, without writing a loop.

You need to find IDs present in expected_ids but missing from actual_ids. Which operator?
# Set comprehension — same brace syntax as dict, no colon
unique_statuses = {r.status for r in test_results}

Interview Q&A

Junior What's the difference between dict[key] and dict.get(key)?
dict[key] raises KeyError if the key doesn't exist — appropriate when a missing key means something is genuinely wrong. dict.get(key) returns None instead (or a custom default via .get(key, default)) — appropriate when the key being absent is an expected, handled case, like an optional field in an API response.
Mid Why is checking membership in a set faster than in a list?
A list is a sequence — checking x in list scans from the start until it finds a match, which is O(n) and gets slower as the list grows. A set (and a dict's keys) uses a hash table: hash(x) computes directly which bucket to check, making membership testing O(1) on average regardless of collection size. For repeated lookups against a large collection, converting it to a set once and checking membership against that is a common, real performance fix.
Mid Why can't you use a list as a dict key or put one in a set?
Both dict keys and set members must be hashable, and Python considers mutable types unhashable by design — if a list's contents changed after insertion, its hash would change too, which would corrupt the hash table's bucket structure (the item would become unfindable at its own stored location). Tuples work as keys precisely because they're immutable and therefore have a hash that's stable for their whole lifetime.
Senior You're comparing two large lists of user IDs for differences in a test — why is this a set problem, not a list problem?
Framed as lists, finding "IDs in A but not B" naively means a nested loop or repeated in checks against B — O(n×m). Converting both to sets turns it into set_a - set_b, a single O(n+m) operation using hash-based lookups internally. Beyond the performance difference, it's also just more readable — -, &, and ^ directly express "missing", "shared", and "mismatched" without a loop obscuring the intent. The only cost is losing duplicates and original order, which usually doesn't matter for an ID-comparison check.

Gotchas

Mutating a dict while iterating it raises RuntimeError for key in my_dict: del my_dict[key] raises RuntimeError: dictionary changed size during iteration. Iterate over a copy of the keys instead: for key in list(my_dict.keys()):.
{} is an empty dict, not an empty set There's no literal shorthand for an empty set — {} always means dict. You have to write set() explicitly. This trips people up constantly when initializing a set-typed variable.
