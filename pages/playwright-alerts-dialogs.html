JavaScript Alerts & Dialogs

Every locator strategy on this site assumes the thing you want is in the DOM. A native alert() or confirm() isn't — it's a browser-level window with no HTML behind it. Inspect it and you'll find nothing, which is why it needs an entirely different mechanism.

Why locators don't work

A JavaScript alert(), confirm(), or prompt() is rendered by the browser itself, not by the page. Right-click and inspect it and there is no element to find — no tag, no class, no id — because it isn't part of the document at all. Every DOM-based tool hits the same wall here; this isn't a Playwright limitation specifically.

So instead of locating it, you register an event handler in advance: "if a dialog ever appears during this test, here's what to do with it." Playwright then handles it automatically whenever it fires.

Illustrative — a native dialog sits above the page, outside the DOM
shop.example.com says

Are you sure you want to continue?

There is no <button> behind that OK. page.get_by_role("button", name="OK") finds nothing and times out — the element genuinely does not exist in the page.

The event listener flow

The ordering is the whole trick: the handler is registered before the click that triggers the dialog. Step through and note that nothing appears at registration time.

What happens if you register the dialog handler after the click that triggers it?

The lambda explained

page.on() takes two arguments: the event name, and a function to call when it fires. The function must accept the dialog as a parameter. Written out longhand:

def handle_dialog(dialog):
    dialog.accept()

page.on("dialog", handle_dialog)      # note: no parentheses — passing the function itself

For a one-line body, defining a named function is overhead. Python's lambda creates an anonymous function — a function with no name, defined inline:

page.on("dialog", lambda dialog: dialog.accept())

Read it as: "a function taking dialog, which returns dialog.accept()." The two forms are equivalent; the lambda is just shorter.

The mistake this prevents Writing page.on("dialog", dialog.accept()) fails — that calls something immediately and passes its result, but page.on needs a function to call later. The lambda wraps the call so it's deferred until the event actually fires.

Dialog API

MemberWhat it does
dialog.accept()Clicks OK / confirms. Accepts an optional string for prompt() dialogs — dialog.accept("my answer").
dialog.dismiss()Clicks Cancel / dismisses. Used to test the "user declined" path.
dialog.messageThe dialog's text. This is assertable — despite the dialog not being in the DOM.
dialog.type"alert", "confirm", "prompt", or "beforeunload".
Beyond this video — you can assert on dialogs The lecture states there's no way to validate a dialog, only to click through it. That's not quite the full picture: dialog.message exposes the text, so you can capture and assert it. A common pattern is to record it from inside the handler: 
messages = []
page.on("dialog", lambda d: (messages.append(d.message), d.accept()))
page.get_by_role("button", name="Confirm").click()
assert messages[0] == "Are you sure you want to continue?"
Also worth knowing: if no handler is registered, Playwright auto-dismisses dialogs by default so tests don't hang — which means a missing handler can silently take the "Cancel" path rather than failing loudly.

Interview Q&A

Junior Why can't you use a normal locator to click OK on a JavaScript alert?
Because the alert is rendered by the browser, not the page — it has no HTML representation at all. There's no element in the DOM to match, so any locator times out. This affects every DOM-based automation tool, not just Playwright. Dialogs are handled via an event handler instead: page.on("dialog", lambda dialog: dialog.accept()).
Mid Why must the dialog handler be registered before the triggering action?
Because it's an event subscription, not a wait. When the dialog fires, Playwright looks for an already-registered handler; if none exists, the handler you register afterwards never sees that event. Registering first is the same principle as expect_popup() being a context manager — subscribe before the trigger so the event can't be missed.
Junior What is a lambda and why is one used here?
A lambda is a Python anonymous function — a function defined inline without a name. page.on() requires a function to invoke when the event fires, and since the handler body is a single call, a lambda avoids defining a separate named function. lambda dialog: dialog.accept() is equivalent to a def handle(dialog): dialog.accept() passed by name.
Mid How would you test the "user clicks Cancel" path?
Register a handler calling dialog.dismiss() instead of accept(), then assert on whatever the application does when the action is declined — the record still exists, no confirmation message appears, and so on. The dialog handling itself is one line; the meaningful assertions are about the app's resulting state.
Senior A colleague says dialogs can't be asserted on, only clicked through. Is that right?
Not entirely. The dialog object exposes message and type, so you can capture the text inside the handler and assert it afterwards — verifying that the confirmation wording is correct, not just that a dialog appeared. Worth also knowing that Playwright auto-dismisses dialogs when no handler is registered, so a forgotten handler silently takes the Cancel path instead of failing loudly, which can make a test pass for the wrong reason.

Gotchas

Register once, applies to everything after page.on("dialog", ...) stays active for the rest of that page's lifetime — every subsequent dialog gets the same treatment. If one step needs Accept and a later step needs Cancel, you'll need page.once(...) (fires a single time) or to remove and re-register the handler.
Silent auto-dismiss With no handler registered, Playwright dismisses dialogs automatically rather than hanging. Convenient, but it means forgetting the handler doesn't produce an obvious error — your test just quietly exercises the Cancel path.
