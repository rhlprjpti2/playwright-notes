Database Design & Constraints

Normalization from 1NF to 3NF via an actual messy table getting progressively split apart, the constraint types that enforce data integrity at the database level rather than trusting application code, and why an index speeds up reads at the direct cost of writes.

Concept

Two competing concerns: normalization organizes data to eliminate redundancy and prevent update anomalies (this page's first topic), while constraints and indexes are the mechanisms that enforce correctness and speed up access once the schema is designed. Real systems intentionally trade some normalization away for query performance — this page covers the rules, not a mandate to follow them absolutely.

Normalization: 1NF, 2NF, 3NF

Start with a genuinely messy, unnormalized table — everything crammed into one place:

order_idcustomer_namecustomer_emailproducts
1Ada Lovelaceada@example.comWidget, Gadget, Gizmo
2Ada Lovelaceada@example.comWidget

1NF — eliminate repeating groups. The comma-packed products column violates 1NF outright: a cell must hold one atomic value, not a list. Split each product into its own row:

order_idcustomer_namecustomer_emailproduct
1Ada Lovelaceada@example.comWidget
1Ada Lovelaceada@example.comGadget
1Ada Lovelaceada@example.comGizmo
2Ada Lovelaceada@example.comWidget

2NF — eliminate partial dependencies. Now in 1NF, but with a composite key (order_id + product), customer_name and customer_email only depend on order_id — not on the full key. Split them into their own table:

ordersorder_items
order_idcustomer_name / emailorder_idproduct
1Ada Lovelace / ada@example.com1Widget, Gadget, Gizmo (3 rows)
2Ada Lovelace / ada@example.com2Widget

3NF — eliminate transitive dependencies. customer_email depends on customer_name (or a customer_id), not directly on order_id — it's one more step removed. Split customers into their own table too:

customers(id, name, email)
orders(id, customer_id REFERENCES customers(id))
order_items(order_id REFERENCES orders(id), product)

Now Ada's email is stored in exactly one row, one place, ever — updating it means changing one row instead of hunting down every order that happens to repeat it.

The actual problem normalization solves In the original unnormalized table, updating Ada's email means finding and updating every single order row — miss one, and the same "customer" now has two different emails on file with no indication which is correct. That's an update anomaly, and it's the concrete, practical reason normalization exists — not an academic exercise for its own sake.
A table stores employee_id, department_id, department_manager_name — with department_manager_name depending only on department_id, not on employee_id directly. What normal form does this violate?

Primary keys and foreign keys

CREATE TABLE customers (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255) UNIQUE NOT NULL
);

CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  customer_id INTEGER REFERENCES customers(id),   -- foreign key
  amount DECIMAL(10,2) NOT NULL
);

A primary key uniquely identifies a row within its own table and can never be NULL. A foreign key is a column referencing another table's primary key, enforcing that orders.customer_id can only ever hold a value that genuinely exists in customers.id — or NULL, if the column allows it, representing "no customer" rather than a broken reference.

UNIQUE, CHECK, NOT NULL, DEFAULT

CREATE TABLE accounts (
  id SERIAL PRIMARY KEY,
  username VARCHAR(50) UNIQUE NOT NULL,        -- no two rows can share a value
  balance DECIMAL(10,2) NOT NULL DEFAULT 0,     -- auto-filled if omitted on INSERT
  status VARCHAR(20) CHECK (status IN ('active', 'suspended', 'closed'))
);

These enforce correctness at the database layer — an INSERT or UPDATE that would violate any of them fails outright, regardless of which application, script, or person issued it. That's the key advantage over enforcing the same rules only in application code: a constraint can't be bypassed by a direct database connection, a different service, or a bug in validation logic upstream.

Indexes — and their cost

An index lets the database jump straight to matching rows instead of scanning every one — same underlying idea as the hash-bucket lookup covered on the Dicts & Sets page, applied to a table column instead of a Python set.

CREATE INDEX idx_users_email ON users(email);
-- Now the same query jumps directly to the matching row — no scan
Indexes aren't free — they cost on every write Every INSERT, UPDATE, or DELETE has to update every index on that table, not just the table's own data. A table with 8 indexes pays that cost 8 times per write. Indexing every column "just in case" is a real anti-pattern — indexes should target columns actually used in WHERE, JOIN, or ORDER BY clauses on queries that run often enough to matter.

Interview Q&A

Junior What problem does normalization actually solve?
Update anomalies caused by redundant data — if the same fact (a customer's email, say) is repeated across many rows, updating it requires finding and changing every copy; missing one leaves inconsistent data with no way to tell which copy is correct. Normalization stores each fact in exactly one place.
Junior What's the difference between a primary key and a unique constraint?
A table can have only one primary key, and it can never be NULL. A table can have multiple UNIQUE constraints, and — depending on the database — a UNIQUE column can typically allow NULL (often more than one, since NULL isn't considered equal to another NULL for uniqueness purposes).
Mid Why not just add an index to every column to be safe?
Every index has to be updated on every write to that table — more indexes means slower INSERT/UPDATE/DELETE, plus additional storage. Indexes should be added deliberately, targeting columns that are actually filtered, joined, or sorted on frequently enough that the read speedup outweighs the write cost.
Senior When would you intentionally denormalize a schema?
When read performance matters more than eliminating redundancy — e.g. storing a pre-computed total on an orders row instead of recalculating SUM(order_items) on every read, accepting the risk of that total drifting out of sync in exchange for not re-aggregating on every query. This is a deliberate, documented trade-off, not a sign the schema was designed incorrectly.

Gotchas

Over-indexing silently slows down writes A schema with an index on every column looks safe but pays a real, compounding cost on every INSERT/UPDATE/DELETE.
A foreign key without an index on the referencing column is a common performance miss The referenced column (usually a primary key) is indexed automatically, but the referencing column (e.g. orders.customer_id) often isn't unless added explicitly — joins on it then fall back to a full scan.
Constraints enforced only in application code can be bypassed A direct database connection, a migration script, or a different service entirely can write data that skips application-level validation. Database constraints are enforced no matter what wrote the data.
