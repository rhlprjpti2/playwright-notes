Handling Child Windows & Popups

A page object only ever knows about the page it was created on. Click a link that opens a new tab, and your existing page variable has no idea that new window exists — you have to explicitly listen for it and capture a fresh page object.

Concept

A page object is scoped to whatever page was open when it was created — by default, that's the page your browser context started on. Clicking a link that opens a separate window or tab does not automatically give your existing page variable access to it. The new window is invisible to it. To work with that new window, you have to explicitly tell Playwright to listen for it, capture the moment it appears, and pull out a brand-new page object scoped to that window specifically.

expect_popup() in depth

The lecture uses this method but doesn't document it. Since "explain how expect_popup works" is a fair interview question, here's the actual API surface.

Signature & return

playwright.sync_api.Page
page.expect_popup(*, predicate=None, timeout=None) # -> EventContextManager[Page]
PartWhat it is
ReturnsAn event context manager — not a Page. You must use it in a with block, then read .value afterward to get the actual Page.
.valueAvailable only after the with block exits. Blocks until the popup is captured, then returns the new Page object.
timeoutMilliseconds to wait for a popup before raising TimeoutError. Defaults to the context's standard timeout (30s unless changed). 0 disables the timeout.
predicateAn optional filter lambda popup: ... — the listener ignores popups that don't satisfy it. This is how you target a specific window when several could open.

Why a context manager and not just a wait?

This is the genuinely interesting part, and a strong interview answer. The obvious-looking alternative has a race condition:

the broken approach — do not do this
page.locator(".blinking-text").click()  # popup may open THIS instant child = page.wait_for_popup()        # too late — event already fired, we missed it

Clicking first and listening second means the popup event can fire in the gap between the two lines, and the listener never sees it — the test then hangs until timeout, intermittently, depending on machine speed. That's a classic flaky test.

The with block eliminates the gap by construction: the listener is subscribed before the triggering action runs, so the event cannot be missed regardless of timing. Every Playwright expect_* method (expect_download, expect_request, expect_navigation, …) follows this same pattern for the same reason.

Interview framing If asked "why is it a with block?", the answer isn't "that's the syntax" — it's race-condition avoidance: subscribe before the trigger so a fast-firing event can't be missed. Naming that shows you understand the design, not just the usage.

Related methods

MethodWhen you'd reach for it
page.expect_popup()The standard case — one popup, triggered by a known action.
page.on("popup", handler)The lower-level event API expect_popup wraps. Fires a callback for every popup — useful for logging or auto-closing unexpected windows across a whole session.
context.pagesA list of every page currently open in the context. Good for finding a specific window after the fact, or asserting how many are open.
context.expect_page()Context-level equivalent — catches a new page opened by any page in the context, not just the one you called it on.
child_page.wait_for_load_state()The popup Page is returned as soon as it's created, which may be before its content has loaded. Call this when you need the page fully ready.
child_page.close()Closes the popup. Worth doing in long test runs so windows don't accumulate.

Why does Playwright use with page.expect_popup(): instead of letting you click first and then call a wait method?

Full example

Locating the trigger link itself uses the same CSS-locator technique from the Core Locators page — a unique class name is often simpler than a full get_by_role call with a long name filter:

page.goto(BASE_URL)

with page.expect_popup() as new_page_info:
    page.locator(".blinking-text").click()   # triggers the popup

child_page = new_page_info.value             # the new window's page object

text = child_page.locator(".red").text_content()
print(text)

Every step that needs to happen on the new window — clicks, fills, assertions — must go through child_page, not page. The original page variable never gains knowledge of the popup; it stays permanently scoped to the base page it started on.

Reading text with text_content()

Distinct from asserting an element is visible (expect(locator).to_be_visible(), already covered on the Auto-Waiting page) — .text_content() actually retrieves and returns the element's text so you can print it, log it, or manipulate it in code:

text = child_page.locator(".red").text_content()
print(text)

This prints the entire matched element's text — if that element wraps more than just the piece you care about (e.g. a whole line containing an email address alongside other words), you get all of it, not just the part you want.

Interview Q&A

Junior Why doesn't your existing page object automatically work on a new tab/window that a click opens?
A page object is scoped to the specific page it was created on — by default, the page your browser context started on. Playwright doesn't automatically expand that scope when a click happens to open a new window; you have to explicitly listen for the new page and capture a separate page object for it.
Mid Walk through what page.expect_popup() actually does, step by step.
It's a context manager that arms an event listener before the action that might open a popup runs. The action (e.g. a click) executes inside the `with` block; if it results in a new page/window opening, the listener captures that new page's info. After the block exits, `.value` on the captured object returns the actual new Page instance, which you then use for all further interaction with that window.
Junior What's the difference between text_content() and a visibility assertion like to_be_visible()?
to_be_visible() checks a boolean condition — is the element rendered and visible — and is what you use for assertions. text_content() actually retrieves and returns the element's text content as a string, for when you need to read, print, log, or further process that text in code rather than just confirm it exists.
Scenario You use the correct child_page for the new window, but a teammate's code uses the original page and their test times out with "element not found." How do you explain what's happening?
The original page object never gained any knowledge that a new window opened — it's still scoped to the base page. When their code searches for an element that only exists in the popup, Playwright's auto-waiting kicks in exactly as designed: it retries, checking visibility repeatedly, and since the element genuinely doesn't exist on that page, it eventually times out and fails. It's not a bug or a special popup-related error — it's the standard actionability-timeout behavior failing for a completely mundane reason: wrong page object.
Mid If two different links could each open a different popup, how would you distinguish which new page you got?
expect_popup() alone just captures whatever popup opened as a result of the wrapped action — fine when only one link is in play. For distinguishing between multiple possible popups, pass a predicate (e.g. lambda p: "documents" in p.url) so the listener only accepts a matching window, inspect properties of the resulting page after capturing it, or use context.pages to enumerate every currently-open page and filter for the one you expect.
Senior Why is expect_popup() a context manager rather than a method you call after the click?
Race-condition avoidance. If you clicked first and then called a wait method, the popup event could fire in the gap between those two statements — the listener would never see it, and the test would hang until timeout, intermittently, depending on machine speed. The with block subscribes the listener before the triggering action executes, so the event cannot be missed regardless of timing. Every Playwright expect_* method (expect_download, expect_request, expect_navigation) uses this pattern for the same reason.
Mid What does expect_popup() actually return, and when is .value available?
It returns an event context manager, not a Page. .value is only meaningful after the with block exits — at that point it blocks until the popup has been captured and returns the new Page object. It also accepts timeout (ms before raising TimeoutError, defaulting to the context timeout) and predicate (a filter so only a matching popup is accepted).
Senior You capture a popup and immediately query an element on it, but get intermittent failures. What's a likely cause beyond using the wrong page object?
The popup Page is returned as soon as the window is created, which can be before its content has finished loading. Auto-waiting covers element actionability, but if the page is still navigating, the DOM you're querying may not be the final one. Calling child_page.wait_for_load_state() (optionally with "networkidle") before querying makes the readiness explicit rather than relying on timing.

Gotchas

Watch out Every step that needs the new window must be written inside the with block if it's part of triggering the popup, or use the resulting child_page variable afterward — reaching for the original page variable anywhere after the popup opens silently searches the wrong page and eventually times out, rather than raising an obvious "wrong page" error.
Watch out text_content() returns the entire matched element's text. If you only want a piece of it (e.g. just an email address inside a longer line of text), you still need ordinary Python string processing afterward — Playwright doesn't parse or extract substrings for you.
