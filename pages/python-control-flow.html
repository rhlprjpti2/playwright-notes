Control Flow

if/for/while look identical to every other language at a glance — the parts that actually differ, and actually come up in interviews, are iterating without index variables and the loop else clause almost nobody expects.

if / elif / else

if response.status_code == 200:
    result = "passed"
elif response.status_code == 404:
    result = "not found"
else:
    result = "failed"

# Ternary — one-line conditional expression
result = "passed" if response.status_code == 200 else "failed"

The ternary form reads as "the value, then the condition, then the fallback" — backwards from most languages' condition ? a : b, which is exactly the kind of thing that trips people up the first few times they read someone else's Python.

for loops without indexes

Python's for loops over the items of an iterable directly — there's no C-style for (i = 0; i < n; i++) at all. If you find yourself writing for i in range(len(items)) just to then do items[i], that's almost always a sign you want the plain form instead.

# Avoid — indexing an iterable you already have
for i in range(len(test_names)):
    print(test_names[i])

# Idiomatic — iterate the items directly
for name in test_names:
    print(name)

enumerate() and zip()

The two situations that do need more than the item itself both have a dedicated built-in, rather than reaching for manual indexing.

# Need the index AND the item → enumerate()
for i, name in enumerate(test_names):
    print(f"{i}: {name}")

for i, name in enumerate(test_names, start=1):   # start counting from 1
    print(f"Test #{i}: {name}")

# Need to walk two lists in parallel → zip()
expected = ["passed", "passed", "failed"]
actual   = ["passed", "failed", "failed"]
for exp, act in zip(expected, actual):
    if exp != act:
        print(f"mismatch: expected {exp}, got {act}")
zip() stops at the shortest iterable If expected has 5 items and actual has 3, zip() silently pairs up only the first 3 and stops — it does not raise an error for the length mismatch. If mismatched lengths should be a test failure in their own right, check len(expected) == len(actual) explicitly before zipping.

while loops

attempts = 0
while attempts < 3 and not element.is_visible():
    time.sleep(1)
    attempts += 1

In Playwright specifically, manual polling loops like this are rarely needed — the whole point of auto-waiting is that the framework already retries actionability checks internally. A hand-rolled while retry loop around a Playwright call is usually a sign of fighting the framework rather than using it.

The loop else clause

Both for and while loops can have an else block — it runs only if the loop completed without hitting a break. This is a genuinely underused feature that maps directly onto a common "search and verify not found" pattern.

for item in cart_items:
    if item.name == "out-of-stock-product":
        print("Found it — should not be in cart")
        break
else:
    print("Confirmed: product correctly absent from cart")

Without else, the same logic needs a separate flag variable set inside the loop and checked afterward — for/else collapses that into the loop itself. It reads oddly the first time ("else... on a for loop?"), which is exactly why it's a favorite "do you actually know Python" interview question.

The walrus operator (:=)

Added in Python 3.8, := assigns a value and returns it in the same expression — useful specifically for avoiding a duplicate call inside a condition.

# Without walrus — calls get_next_row() twice, or needs an extra line
row = get_next_row()
while row is not None:
    process(row)
    row = get_next_row()

# With walrus — assign and test in one line
while (row := get_next_row()) is not None:
    process(row)

It's a style choice more than a necessity — plenty of production code never uses it — but it shows up often enough in modern Python (and in interview "what does this do" snippets) to be worth recognizing on sight.

Interview Q&A

Junior Why does idiomatic Python avoid for i in range(len(items))?
Python's for loop iterates over the items of an iterable directly, so for item in items: already gives you each element without needing an index to look it up. Using range(len(items)) just to then index back into the list is unnecessary — and if you also need the index, enumerate(items) gives you both the index and the item together, more directly than manual indexing.
Junior What does zip() do, and what happens with mismatched-length inputs?
zip() pairs up corresponding items from two or more iterables so they can be looped over together. If the iterables have different lengths, zip() stops as soon as the shortest one is exhausted — it does not raise an error or pad the shorter one, so a length mismatch fails silently unless checked for separately.
Mid What does the else clause on a for loop actually do?
It runs only when the loop completes all its iterations without hitting a break. It's most useful for a "search, and confirm not found" pattern: loop looking for something, break if found, and let else handle the "loop finished, nothing matched" case — avoiding a separate boolean flag variable to track whether a match occurred.
Mid What problem does the walrus operator (:=) solve?
It lets you assign a value and use it in the same expression, most commonly inside a while or if condition — avoiding calling the same function twice (once to test it, once to use the result) or writing an extra assignment line before the condition. It's purely a readability/DRY tool, not something that changes what's possible — everything it does could already be written with an extra line.

Gotchas

Mutating a list while iterating it skips elements for item in items: items.remove(item) silently skips every other element, because removing an item shifts everything after it down one index while the loop's internal position doesn't adjust. Iterate over a copy instead — for item in items[:]: — or build a new list via a comprehension rather than mutating in place.
range(n) is not the values 0 to n range(5) produces 0, 1, 2, 3, 4 — 5 is excluded, matching the same "stop is exclusive" convention as slicing. This causes the same off-by-one confusion in both places, for the same reason.
